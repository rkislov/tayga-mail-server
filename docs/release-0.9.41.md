# Tayga Mail 0.9.41 — массовые операции с письмами

Выделенные письма обрабатываются пакетами с индикатором прогресса. Ошибка одного письма больше не прерывает оставшуюся выборку: интерфейс показывает число успешных операций и сохраняет выделение доступных неудачных элементов.

- Для 49 писем веб-клиент выполняет пять запросов вместо 49. API ограничивает пакет 50 элементами, проверяет владельца и исходную папку каждого письма.
- Архивирование сохраняет новый файл, затем одной транзакцией меняет папку, UID, путь и размер; исходный файл удаляется после успешного сохранения. Ошибки и конкурирующие перемещения не оставляют частично обновлённую запись.
- Повторное архивирование в той же папке сохраняет путь и UID. Неизменившийся текст не разбирается и не индексируется повторно.
- IMAP STORE меняет флаги в базе, не переименовывая файл во время чтения и архивирования. База остаётся источником флагов, как для веба, EWS и ActiveSync; экспорт только Maildir без базы не переносит актуальные флаги.
- Сбой перемещения в корзину возвращает ошибку; окончательного удаления при таком сбое нет. Повтор старого пакетного запроса не удаляет письмо, уже перемещённое в корзину.
- Подробная ошибка с идентификатором письма остаётся в серверном журнале. Пользователю показывается понятный результат без внутренних путей; длинный текст переносится в пределах окна.
- Очередь обучения Rspamd при переходах в спам и обратно сохраняется в той же транзакции.

Проверки: полный Go test suite; целевые race-тесты; SQLite с имитацией отказа транзакции; PostgreSQL; IMAP STORE/FETCH; изолированный браузер на ширине 390 и 1280 пикселей. Проверены частичный пакет из 49 писем, повторные/конкурирующие операции, чужие письма и неверные запросы. Пользовательские письма для тестов не отправлялись и не перемещались.

Релиз включает [SASL2/SCRAM и WebSocket из 0.9.40](release-0.9.40.md). При обновлении с 0.9.39 применяется добавочная миграция 061; отдельной миграции 0.9.41 нет. Обновление не восстанавливает автоматически файлы, отсутствовавшие до установки: такие записи сохраняются и не мешают обработке остальных писем. Перед обновлением нужна проверенная резервная копия базы, конфигурации и предыдущего бинарника.
