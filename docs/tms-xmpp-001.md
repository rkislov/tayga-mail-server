# Техническое задание: Встраивание XMPP с E2E-шифрованием в Tayga Mail Server

**Номер документа:** TMS-XMPP-001  
**Версия:** 1.0  
**Связанный документ:** Техническое задание на Tayga Mail Server v2.0 (раздел 3, дополнение TMS-DOP-001)

## 1. Назначение и область применения

Настоящее ТЗ определяет требования к встроенному XMPP-серверу в составе Tayga Mail Server с обязательной поддержкой **сквозного шифрования (End-to-End Encryption, E2EE)** на основе протокола OMEMO (XEP-0384), использующего криптографическое ядро Signal (Double Ratchet + X3DH).

**Ключевой принцип:** XMPP-сервер Tayga не должен иметь доступа к содержимому зашифрованных сообщений. Шифрование и дешифрование выполняются исключительно на клиентских устройствах. Сервер отвечает только за маршрутизацию, хранение зашифрованных «конвертов» и публикацию открытых ключей.

## 2. Архитектурные требования

### 2.1. Модуль XMPP в едином бинарнике

XMPP-модуль компилируется в состав единого Go-бинарника Tayga, использует общий слой аутентификации (LDAP/OIDC/MFA) и общий слой хранения (SQLite/PostgreSQL).

### 2.2. Обязательные протоколы и расширения

| Компонент | Стандарт | Назначение |
|-----------|----------|------------|
| Ядро XMPP | RFC 6120 / 6121 | Потоки, аутентификация, сообщения, Presence |
| OMEMO | XEP-0384 | E2EE на основе Signal (Double Ratchet) |
| PubSub | XEP-0060 | Публикация ключевых бандлов устройств |
| PEP | XEP-0163 | Персональные события (ключи OMEMO) |
| MAM | XEP-0313 | Архивирование зашифрованных сообщений |
| Carbons | XEP-0280 | Синхронизация между устройствами пользователя |
| S2S | RFC 6120 §4 | Федерация с другими XMPP-серверами |

## 3. Требования к E2E-шифрованию (OMEMO / Signal)

### 3.1. Криптографические гарантии

Сервер обязан обеспечить инфраструктуру для следующих криптографических свойств, реализуемых на клиентах:

| Свойство | Описание | Стандарт |
|----------|----------|----------|
| **Конфиденциальность** | Только отправитель и получатель могут прочитать содержимое | X3DH + Double Ratchet |
| **Прямая секретность (Forward Secrecy)** | Компрометация текущих ключей не раскрывает предыдущие сообщения | Double Ratchet |
| **Восстановление после компрометации (Post-Compromise Security)** | Сессия восстанавливается после нескольких раундов обмена | Double Ratchet |
| **Аутентификация и целостность** | Каждое сообщение подписано; подделка невозможна | Ed25519 |
| **Асинхронность** | Отправка возможна, когда получатель офлайн | PreKeys |

### 3.2. Роль сервера в OMEMO

Сервер **не выполняет** шифрование/дешифрование. Его функции:

1. **Хранение ключевых бандлов** — публикация и выдача открытых ключей (Identity Key, Signed PreKey, PreKeys) через PubSub/PEP.
2. **Хранение списка устройств** — каждый клиент генерирует случайный Device ID (UInt32); сервер хранит список активных устройств пользователя.
3. **Маршрутизация зашифрованных сообщений** — сервер видит только XML-структуру `<encrypted>` с заголовками для каждого устройства-получателя; содержимое непрозрачно.
4. **Поддержка MAM** — архив хранит зашифрованные сообщения как есть; при синхронизации нового устройства сервер отдаёт архив, клиент расшифровывает.

### 3.3. Формат зашифрованного сообщения

Сервер должен корректно обрабатывать и маршрутизировать сообщения следующей структуры (упрощённо):

```xml
<message to="bob@example.com" from="alice@example.com">
  <encrypted xmlns="urn:xmpp:omemo:2">
    <header sid="alice_device_id">
      <key rid="bob_device_1" kex="true">base64_encrypted_key</key>
      <key rid="bob_device_2">base64_encrypted_key</key>
      <iv>base64_iv</iv>
    </header>
    <payload>base64_encrypted_content</payload>
  </encrypted>
</message>
```

Сервер не должен пытаться валидировать криптографические поля или модифицировать их.

### 3.4. Управление ключами и устройствами

| Требование | Описание |
|------------|----------|
| Публикация Identity Key | При первом подключении устройство публикует долгосрочный открытый ключ |
| Генерация Signed PreKey | Устройство публикует подписанный среднесрочный ключ |
| Батч PreKeys | Устройство загружает набор одноразовых PreKeys; сервер выдаёт их по одному при инициализации сессии |
| Список устройств | Сервер отдаёт актуальный список Device ID пользователя |
| Отзыв устройства | При удалении устройства сервер удаляет его ключевой бандл из PubSub |

### 3.5. Интеграция с MAM (архив сообщений)

Требование XEP-0384: архив должен хранить зашифрованные сообщения, чтобы новые устройства могли получить историю переписки.

- MAM хранит полный XML-конверт `<encrypted>` без изменений.
- При запросе истории клиент получает архив и локально расшифровывает каждое сообщение.
- Forward Secrecy и backup/restore «не дружат»: клиент должен предупредить пользователя, что восстановление резервной копии ключей ослабляет гарантии.

## 4. Go-реализации криптографического ядра

### 4.1. Выбор библиотеки

Для **клиентской** части Tayga (веб-интерфейс, десктоп-клиент, CLI) требуется реализация Signal/OMEMO. Варианты на 2026:

| Библиотека | Статус | Особенности |
|------------|--------|-------------|
| **GoCodeAlone/libsignal-go** | Активная | Pure-Go, wire-compatible с libsignal; **AGPL-3.0** |
| jim-ww/omemo-go + xochimilco | Активная | OMEMO-параметризованный Double Ratchet; **GPL-3.0** |
| crossle/libsignal-protocol-go | Архивная | Базовая реализация |
| go.mau.fi/libsignal | Архивная | Форк mautrix |

**Лицензионное ограничение Tayga (Apache-2.0):** AGPL/GPL нельзя линковать в единый серверный бинарник. Крипто-ядро OMEMO — только в клиентах (WASM/JS или отдельный AGPL-артефакт). Сервер хранит opaque PEP/MAM.

### 4.2. Компоненты для интеграции (клиент)

Tayga-клиент должен предоставить персистентные реализации:

- `IdentityKeyStore` — доверенные идентификационные ключи контактов
- `PreKeyStore` / `SignedPreKeyStore` / `SessionStore` — локальное состояние Double Ratchet

Схема на **клиенте** (IndexedDB / локальный store), не на сервере: изоляция по `user_id` + `device_id`. На сервере — только публичные PEP-бандлы и opaque MAM.

## 5. Требования к клиентам (для экосистемы Tayga)

### 5.1. Веб-клиент (встроенный в Tayga)

OMEMO на стороне браузера (WASM или JS). Приватные ключи только в IndexedDB.

### 5.2. Внешние клиенты

Совместимость: Gajim, Conversations, Dino, Siskin IM, Monal (OMEMO).

## 6. Нефункциональные требования

### 6.1. Безопасность

| Требование | Описание |
|------------|----------|
| Сервер не видит plaintext | Содержимое зашифровано на клиенте |
| TLS для транспорта | TLS 1.2+ для C2S и S2S |
| Аутентификация | SASL с поддержкой OIDC/OAuth2 (XOAUTH2) |
| Изоляция тенантов | Ключевые бандлы и сессии изолированы по домену |
| Аудит | Логирование операций PubSub (без содержимого) |

### 6.2. Производительность

| Метрика | Целевое значение |
|---------|------------------|
| Публикация ключевого бандла | < 100 мс |
| Выдача ключей получателя | < 50 мс |
| Маршрутизация сообщения | < 20 мс |
| Одновременных XMPP-сессий | ≥ 1000 на узел |

### 6.3. Совместимость

- OMEMO namespace: `urn:xmpp:omemo:2`
- Legacy namespace `eu.siacs.conversations.axolotl` для обратной совместимости

## 7. Ограничения и известные проблемы

| Ограничение | Описание |
|-------------|----------|
| Forward Secrecy vs Backup | Восстановление ключей из бэкапа ослабляет FS |
| Race condition при catch-up | При MAM возможна двойная обработка PreKey |
| PFS в групповых чатах | OMEMO для MUC не даёт полную PFS всем сразу |
| Deniability | OMEMO не даёт правдоподобного отрицания (в отличие от OTR) |

## 8. Критерии приёмки

| № | Критерий | Метод проверки |
|---|----------|----------------|
| AC-OMEMO-01 | Публикация ключевого бандла | Клиент публикует Identity Key + Signed PreKey + PreKeys через PubSub |
| AC-OMEMO-02 | Установка сессии | Alice получает бандл Bob, инициализирует сессию, отправляет первое сообщение |
| AC-OMEMO-03 | Расшифровка на другом устройстве | Bob на втором устройстве; история через MAM |
| AC-OMEMO-04 | Групповое E2EE | MUC с OMEMO; сервер не видит plaintext |
| AC-OMEMO-05 | Forward Secrecy | Компрометация текущих ключей не раскрывает прошлые |
| AC-OMEMO-06 | Верификация отпечатков | Сравнение fingerprint |
| AC-OMEMO-07 | Совместимость | Gajim ↔ Conversations через Tayga |
| AC-OMEMO-08 | S2S федерация | OMEMO через федерацию |
