# SASL2 и SCRAM в XMPP

Начиная с 0.9.40 Tayga поддерживает SASL2 (`urn:xmpp:sasl:2`), SCRAM-SHA-256 и SCRAM-SHA-256-PLUS. После успеха SASL2 сервер отправляет новые stream features без перезапуска XML-потока. Привязка ресурса и Stream Management выполняются обычными отдельными запросами; Bind 2, FAST и inline resumption не объявляются.

## Транспорты и защита

- STARTTLS на 5222 и прямой TLS на 5223: SCRAM с `tls-exporter`; `tls-server-end-point` доступен для сертификатов с определённым RFC 5929 алгоритмом хеширования. Сертификат фиксируется при handshake, поэтому обновление сертификата не меняет привязку уже открытого соединения. TLS 1.2 exporter допускается только когда Go разрешает его использование, включая проверку Extended Master Secret.
- HTTPS WebSocket: SASL2 и обычный SCRAM без PLUS. Browser API не предоставляет TLS exporter. TLS завершается на Tayga; cookies не заменяют SASL.
- В server-first SCRAM включён подписываемый полным обменом хеш `h` из XEP-0474: список механизмов и типов привязки. Подмена этого списка нарушает проверку доказательства клиента. Клиент также должен проверять хеш и серверное доказательство. PLAIN по-прежнему зависит от защиты TLS и не получает защиты SCRAM.
- Отклоняются неверные доказательства, чужая authorization identity, подмена nonce/канала, дублирующиеся параметры, неизвестные обязательные расширения и посторонние stanzas посреди входа. Размер SASL-данных ограничен. Пароли, доказательства, ключи и исходные XML-запросы не записываются в диагностические сообщения.

## Переход существующих учётных записей

Хеш Argon2 нельзя преобразовать в SCRAM. После успешного XMPP-входа по паролю через TLS сервер сохраняет отдельные SCRAM StoredKey/ServerKey. Открытый пароль не сохраняется. Новый механизм становится доступен при следующем подключении. Учётную запись и ключи OMEMO удалять не нужно.

Новые локальные пользователи, созданные через администрирование, и новые пароли устройств получают SCRAM-данные сразу. Изменение основного пароля через профиль или администрирование обновляет Argon2 и SCRAM одной транзакцией. Пароли устройств имеют независимые ключи; случайная соль общая в пределах одной учётной записи и не меняется при смене основного пароля. PBKDF2-SHA-256 использует 32768 итераций. Верификаторы тоже являются чувствительными данными: резервные копии БД должны быть защищены.

SCRAM объявляется только после TLS, для корректного bare JID в stream `from`, когда готовы **все разрешённые пароли** этой учётной записи. Старый пароль устройства сначала должен пройти успешный вход через TLS; его отзыв также устраняет эту зависимость. Без `from` остаются PLAIN/X-OAUTH2. Такой выбор соответствует XEP-0388; различие возможностей может раскрывать наличие подготовленной учётной записи, но не её секреты. Механизм выбирает клиент — SASL2 PLAIN не означает автоматического использования SCRAM.

LDAP-пароли не кешируются как SCRAM: каждый обычный вход продолжает проверяться через LDAP. Для LDAP SCRAM доступен с паролями устройств при включённой политике «только пароли устройств». TOTP-политика продолжает запрещать основной пароль в протоколах; scoped XMPP-пароли сохраняют прежнее поведение. Passkey относится к веб-входу.

При отзыве устройства его SCRAM-ключи удаляются одной транзакцией с отзывом, соединения закрываются. Перед регистрацией SCRAM-сессии заново проверяются версия пароля, статус пользователя и политика доступа. Вход, начатый до отзыва или смены пароля, не может завершиться со старым доказательством.

Низкоуровневый импорт только Argon2-хеша не создаёт SCRAM-ключей. После такого восстановления клиент с закреплённым требованием SCRAM может отказаться от PLAIN: восстановите полную БД с таблицами `xmpp_scram_accounts`/`xmpp_scram_keys` либо задайте новый пароль через штатный интерфейс. Не обходите предупреждение клиента отключением проверок. После появления SCRAM-pinning откат к версии без SCRAM тоже потребует отдельного плана совместимости.

## Проверки

Проверены реальный TLS 1.2/1.3, STARTTLS/прямой TLS, SASL1 и SASL2, WebSocket, bind/ping, независимый SCRAM-клиент xdg-go, фиксированный вектор RFC 7677, неверные пароль/привязка/nonce/доказательство, подмена `h`, отзыв и смена пароля между challenge/response, LDAP/TOTP/device-only, первичный переход с PLAIN. Транзакции и откаты при ошибках проверяются на SQLite и PostgreSQL; гонки — через Go race detector.

Команды: `go test ./...`; `go test -race ./internal/xmpp -run '^(TestSASL2|TestSCRAM)'`; `TAYGA_TEST_BOOKING_POSTGRES_DSN=postgres://... go test -race ./internal/storage -run '^TestXMPP(SCRAM|Device)'`. PostgreSQL должен быть тестовым: каждый тест создаёт и удаляет собственную схему.

Поведение согласовано с исходниками Monal 6.4.24 (build 1101), включая `from`, server proof, signed mechanism list и отсутствие stream restart. Приёмка нового входа в реальных Monal/Conversations фиксируется отдельно после установки; результаты тестового клиента её не заменяют.

Нормативные источники: [XEP-0388](https://xmpp.org/extensions/xep-0388.html), [XEP-0440](https://xmpp.org/extensions/xep-0440.html), [XEP-0474](https://xmpp.org/extensions/xep-0474.html) (experimental), [RFC 7677](https://www.rfc-editor.org/rfc/rfc7677), [RFC 9266](https://www.rfc-editor.org/rfc/rfc9266), [RFC 5929](https://www.rfc-editor.org/rfc/rfc5929).
