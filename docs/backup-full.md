# Полная резервная копия SQLite

Начиная с 0.9.42 доступны `backup-full`, `verify-full`, `restore-full` и
`backup-keygen`. Это физическая копия остановленной установки: вся SQLite-база
со всеми таблицами и весь каталог установки, включая Maildir, `files/`,
`file-state/` (версии, корзина и загрузки), вложения календаря и заметок,
конфигурацию, `secrets.key`, TLS/ACME и DKIM-ключи. Идентификаторы, флаги писем,
права доступа, состояния синхронизации, история XMPP, опубликованные OMEMO-ключи
и настройки сохраняются вместе.

Команды `backup`/`restore` остаются прежним частичным экспортом пользователей и
почты. Они не заменяют полную копию и не выполняют полную миграцию SQLite → PostgreSQL.

## Поддерживаемая схема

- Локальная SQLite; все данные и ключи находятся внутри одного явно указанного
  каталога, например `/var/lib/tayga`. Пути YAML и перекрывающих его настроек БД
  должны быть абсолютными и находиться внутри него.
- Создание и восстановление проверены на Linux и macOS. Атомарное опубликование
  восстановленного каталога реализовано для этих ОС; на других ОС `restore-full`
  отказывается от установки. Файлы в архиве не исполняются.
- PostgreSQL, S3 и пути/символические ссылки за пределы каталога требуют другой
  согласованной процедуры. Этот режим явно отказывает, а не выпускает неполный
  архив под видом полного. Ссылки внутри каталога также отклоняются.
- Внешние Redis/Rspamd, антивирус, LDAP, Collabora и SMTP/DLP-шлюз резервируются
  отдельно. Закрытые OMEMO-ключи браузеров/телефонов на сервере не хранятся.
- Архив и закрытый ключ восстановления хранятся **вне** каталога установки;
  архив следует копировать за пределы сервера/площадки. Каталог копируется
  целиком: вложенные старые бэкапы тоже попадут в него, если их туда поместить.

## Ключ восстановления

Выполнить на доверенной машине администратора, а не на почтовом сервере:

```sh
umask 077
mkdir -p ~/.config/tayga-backup
tayga-mail backup-keygen -out ~/.config/tayga-backup/identity.txt
```

Команда печатает только открытый получатель `age1…`. Его передают серверу.
Закрытый ключ из `identity.txt` хранится отдельно и нужен для проверки и
восстановления. Существующий файл ключа никогда не перезаписывается.
Шифрование использует формат [age](https://pkg.go.dev/filippo.io/age), X25519;
незашифрованный промежуточный архив не создаётся.

## Создание копии

Остановить службу, фоновые задания, другие экземпляры Tayga и внешние инструменты,
изменяющие эту базу или файлы. При первом обновлении с версии до 0.9.42 особенно
важна явная остановка: старый процесс ещё не использует блокировку обслуживания.
Сначала установить новую версию и проверить её запуск, затем выполнить процедуру.

```sh
sudo systemctl stop tayga
sudo /var/lib/tayga/bin/tayga-mail backup-full \
  -root /var/lib/tayga \
  -config /var/lib/tayga/config/tayga.yaml \
  -out /var/backups/tayga/full-2026-11-01.tar.gz.age \
  -recipient age1_REPLACE_WITH_PUBLIC_RECIPIENT
sudo systemctl start tayga
```

Запуск службы выполняется и при ошибке копирования; автоматизирующий скрипт
должен обеспечивать это через `trap`/`finally` и сохранять код ошибки бэкапа.
Не держать службу выключенной на время передачи архива на другую площадку.

Все SQLite-подключения новой Tayga держат общую файловую блокировку. Полная
копия требует исключительную блокировку, выполняет WAL checkpoint, проверяет
SQLite и удерживает SQL-блокировку записи до окончания копирования. Пока она
работает, новый процесс Tayga не откроет базу. Это локальная защита обслуживания,
не распределённый fencing и не разрешение на SQLite через NFS/SMB.

Каждый файл получает SHA-256 и размер в зашифрованном манифесте. Недостающий
файл, на который ссылается письмо/календарь/заметка, отсутствие серверного ключа,
ошибка чтения, изменение файла или невозможность завершить запись прерывают
операцию. Частичный архив удаляется; существующий архив не перезаписывается.
Успешное создание ещё не является приёмкой восстановления.

## Проверка на отдельной машине

```sh
tayga-mail verify-full \
  -in /srv/backups/full-2026-11-01.tar.gz.age \
  -identity ~/.config/tayga-backup/identity.txt \
  -scratch /srv/restore-tests \
  -max-bytes 107374182400
```

Родительский каталог `-scratch` должен существовать и иметь достаточно места
для полного распакованного дерева. Лимит по умолчанию — 100 GiB; для большей
установки задаётся соответствующий `-max-bytes`.

Проверяются аутентификация шифротекста до EOF, gzip, манифест, все файлы,
`quick_check`, `foreign_key_check`, количество записей во всех таблицах,
ссылки на содержимое и пути серверных ключей. После проверки временное дерево
удаляется. Службы и рассылки не запускаются. Усечённый архив, неверный ключ,
дубли путей, `../`, ссылки, специальные файлы и превышение лимита отклоняются.

## Восстановление

```sh
tayga-mail restore-full \
  -in /srv/backups/full-2026-11-01.tar.gz.age \
  -identity ~/.config/tayga-backup/identity.txt \
  -target /srv/recovered-tayga
```

`-target` должен отсутствовать; существующий каталог, даже пустой, не
перезаписывается. Данные проверяются в закрытом промежуточном каталоге и
публикуются атомарно без замены существующего пути. При переносе меняются
локальные пути в конфигурации, настройках БД и ссылках хранилища; исходный
зашифрованный архив не меняется. Внешние адреса, DNS-имя и public URL сохраняются.

Команда **не запускает сервер**. На тестовом узле заблокировать исходящий трафик
и обращения к рабочему LDAP/SMTP/XMPP/внешним почтовым аккаунтам до запуска:
восстановленная база содержит реальные очереди и учётные данные. Для аварийного
ввода в эксплуатацию настроить владельца файлов (например `chown -R tayga:tayga`),
unit/пути, сеть, DNS и сертификаты, отключить прежний узел и проверить readiness.
Не запускать два независимых экземпляра восстановленной почтовой базы.

Использовать бинарник совместимой версии, указанный в манифесте; автоматического
обновления схемы при создании и проверке архива нет. После реального запуска
обычные миграции приложения могут изменить восстановленную базу.

## Приёмка

Изолированный автоматический стенд создаёт пользователей, письмо, календарь с
вложением, задачу, права на ящик/файл, историю и публичные ключи XMPP, группу,
push-ключи, версии и корзину файлов, TLS/DKIM и серверный секрет. Исходное дерево
становится недоступным перед восстановлением. Проверяются сохранность файлов,
вход через слой аутентификации, ACL, идентификаторы и ключи. Отдельно проверены
потоковый перенос файла 75 MiB, повреждения и ограничения архива.

Эта проверка не заменяет восстановление копии рабочей установки на отдельном
узле с замером времени и клиентской приёмкой. До неё нельзя обещать универсальные
RPO/RTO или полноту восстановления PostgreSQL/S3.
