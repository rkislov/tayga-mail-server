# Tayga между двумя площадками

Базовая группа ресурсов и установка узлов описаны в [инструкции одной площадки](ha-single-site.md). На каждой площадке — один узел приложения; на независимой третьей — арбитр. **Одновременно работает только одна Tayga и одна БД.** Общие данные, ограничения текущей реализации и условия RPO/RTO — в [ha.md](ha.md).

## До выбора репликации

Зафиксировать RTT, потери, пропускную способность и пиковый объём записи между площадками, требования RPO/RTO, ёмкость очереди/файлов и время полного resync. Синхронная репликация добавляет сетевую задержку к записи; допустимый RTT определяется испытаниями выбранной СХД и нагрузки, универсального числа для Tayga нет. Репликация должна успевать после восстановления площадки при продолжающейся рабочей нагрузке.

Отдельно спроектировать доступ клиентов. При растянутой L2-сети можно использовать VIP из предыдущего примера. При L3-площадках один IPaddr2 не переносит маршрутизацию: нужен управляемый BGP/маршрут, отказоустойчивый frontend/NAT либо иная инфраструктура, направляющая трафик только к владельцу ресурсов. DNS-переключение зависит от кешей и не заменяет fencing. Проверить SMTP outbound IP/PTR/SPF, MX, TLS-сертификаты и все клиентские порты в обоих направлениях. Сам frontend и канал к нему не должны быть единой точкой отказа.

## Вариант А: синхронный MetroLUN

1. У поставщика СХД подтвердить: стабильный WWID, синхронную запись и порядок flush, поведение при потере связи/площадки, независимый storage witness, правила выбора владельца, ALUA/multipath и поддерживаемые ОС. «Одинаковый номер LUN» без этих гарантий не равен MetroLUN.
2. Представить том двум узлам с поддерживаемым multipath. Обычная FS смонтирована только на владельце группы Pacemaker. Репликация в СХД не разрешает двум ext4/XFS или SQLite писать одновременно.
3. Storage witness и Corosync qnetd разместить вне общего отказа двух площадок. Они решают разные задачи. Документировать, как их решения согласуются: сторона, сохранившая право на диск, должна иметь кворум приложения и возможность fence второго узла. Если победители расходятся, правильный результат — остановка сервиса, а не принудительная запись на неподтверждённую копию.
4. Настроить аппаратный fencing обоих узлов через канал, не зависящий только от межплощадочного линка. При невозможности гарантированно изолировать старого писателя автоматический запуск на другой стороне запрещён.
5. Создать группу FS → (PostgreSQL для нового развёртывания) → Tayga → сервисный маршрут/VIP. Все постоянные данные перемещаются вместе. Не добавлять одновременно DRBD поверх MetroLUN без отдельного проекта поставщика.
6. Испытать разрыв межплощадочной связи при живых узлах, потерю питания площадки, потерю storage witness, потерю qnetd, асимметричную доступность диска и управления питанием. Для каждого случая должна быть однозначна сторона, которой разрешено писать, или подтверждённая остановка обеих.

Возврат площадки: старый узел остаётся standby; дождаться восстановления путей и полного синхронного состояния СХД, сверить отсутствие второго writer. Только затем разрешить узлу участвовать. Не копировать старые данные поверх активного тома и не выполнять принудительный failback до resync.

## Вариант Б: DRBD вместо MetroLUN

DRBD 9 Protocol C реплицирует блочное устройство между двумя локальными дисками. Третий diskless-узел участвует в DRBD quorum, но не хранит резервную копию. На нём можно разместить qnetd при независимых питании и сети. DRBD quorum и Corosync quorum настраиваются и проверяются отдельно.

Использовать поддерживаемые совместно версии ядра, DRBD-модуля, drbd-utils и OCF-агента `ocf:linbit:drbd`; наличие только утилиты drbdadm не доказывает наличие DRBD 9 в ядре. Проверить `/proc/drbd`, `drbdadm --version`, доступность ресурса в `pcs resource describe ocf:linbit:drbd`. Версии пакетов/репозиторий выбрать по поддержке вашей ОС у LINBIT.

[Пример ресурса](../deploy/ha/drbd-tayga.res.example) содержит два дисковых узла и один diskless, Protocol C, `auto-promote no`, majority quorum и `on-no-quorum suspend-io`. Адреса, backend-устройства и node-id заменить на реальные, одинаковую конфигурацию установить на все три узла. `allow-two-primaries` не включать. Защитить сеть репликации; если трафик проходит недоверенную сеть, применить поддерживаемое шифрование транспорта/VPN. DRBD не шифрует данные автоматически.

### Первичная подготовка пустых дисков

Эти операции создают метаданные и файловую систему. Они допустимы **только на выделенных пустых устройствах**, после проверки серийных номеров и off-site backup. Для переноса существующих данных сначала создать отдельную реплику и затем копировать весь согласованный набор.

1. На всех узлах проверить конфигурацию `drbdadm dump tayga`; на двух дисковых узлах выполнить `drbdadm create-md tayga`. Поднять ресурс `drbdadm up tayga` на всех трёх узлах. Для diskless не создавать метаданные на чужом физическом диске.
2. Только при первой инициализации пустого кластера выбрать источник и выполнить на нём `drbdadm primary --force tayga`. Это не штатная команда аварийного восстановления; никогда не повторять её вслепую после split-brain.
3. Дождаться состояния обеих дисковых копий UpToDate по `drbdsetup status tayga --verbose --statistics`. Создать ext4/XFS на `/dev/drbd0` **один раз**, не на backend-дисках. На первом узле временно смонтировать, перенести полный набор данных, создать маркер и проверить права/ключи.
4. Размонтировать FS, перевести ресурс обратно в Secondary. Убедиться, что нет открывших его приложений. На двух узлах приложения передать управление DRBD Pacemaker; diskless-witness поддерживает подключение отдельной службой DRBD без роли Primary. Не настраивать два конкурирующих менеджера одного ресурса.

### Pacemaker

Для двух узлов приложения повторить настройку qdevice и fencing из основной инструкции. На этапе maintenance создать promotable-ресурс:

```sh
sudo pcs resource create drbd-tayga ocf:linbit:drbd drbd_resource=tayga \
  op monitor interval=15s role=Promoted \
  op monitor interval=30s role=Unpromoted
sudo pcs resource promotable drbd-tayga \
  promoted-max=1 promoted-node-max=1 clone-max=2 clone-node-max=1 notify=true
```

Группа `tayga-stack` использует `/dev/drbd0` вместо LUN. После создания группы добавить ограничения:

```sh
sudo pcs constraint colocation add tayga-stack with Promoted drbd-tayga-clone INFINITY
sudo pcs constraint order promote drbd-tayga-clone then start tayga-stack
```

Проверить фактическое имя clone, поддерживаемый синтаксис ролей и ограничения через `pcs status --full` и `pcs constraint config`. При старой версии PCS используются прежние названия ролей Master/Slave; не смешивать варианты. Остановка должна идти VIP → Tayga → БД → FS → demote DRBD. Не запускать приложения при незавершённом fencing или отсутствии дискового quorum.

**Компромисс после потери реплики:** оставшийся дисковый узел и diskless witness могут сохранить quorum и продолжить запись на единственную копию. Последующая потеря этого диска уже не покрывается синхронной репликацией. Если требуется запрещать такое продолжение, отдельно настроить и испытать `quorum-minimum-redundancy 2` на поддерживающей его версии DRBD; это уменьшает доступность при потере одной дисковой копии. Зафиксировать выбранный режим в SLA.

При потере quorum `suspend-io` может блокировать БД. Проверить monitor timeout, остановку и fencing в этом состоянии; не лечить зависший I/O ручным двойным promotion. При расхождении реплик сначала остановить доступ, сохранить обе копии для анализа и определить авторитетную. Использовать процедуру восстановления LINBIT для подтверждённого случая; команды discard/overwrite данных здесь намеренно не автоматизированы.

[DRBD 9 User Guide](https://linbit.com/drbd-user-guide/drbd-guide-9_0-en/), [drbd.conf](https://linbit.com/man/v9/?linbitman=drbd.conf.5.html).

## Если синхронная связь недоступна

Для текущей архитектуры безопаснее **асинхронный аварийный резерв с согласованными контрольными точками**, а не независимые PostgreSQL streaming replication и rsync файлов. Независимая репликация может дать запись письма в БД без тела, файл без версии или несовпадающие состояния очередей.

1. На активной стороне создать согласованный snapshot всего состояния: остановить всех писателей, завершить БД/сделать штатный checkpoint по выбранной процедуре, flush, snapshot тома; снова запустить сервис. Для online-снимка согласование отдельно разрабатывается и испытывается.
2. Передать snapshot в резервное хранилище с проверкой контрольных сумм. Отметить доступную **полную** контрольную точку только после получения БД, файлов, ключей и конфигурации. Хранить несколько поколений и отдельную неизменяемую резервную копию.
3. При аварии подтвердить остановку/изоляцию основной площадки. Вручную активировать последнюю полную точку, проверить целостность, перенаправить клиентов. RPO — возраст этой точки плюс время её передачи; RTO включает восстановление и смену маршрута.
4. Не запускать старую площадку автоматически после её возврата. Сначала синхронизировать её с новым владельцем и проверить план обратного переключения. Потерянные между точками изменения клиентов могут требовать повторной синхронизации.

Отдельные кластеры PostgreSQL/объектного хранилища возможны как будущая архитектура, но требуют согласованного протокола записи приложения, идемпотентных очередей и испытаний. Наличие WAL-репликации PostgreSQL само по себе не делает файловый сервис или XMPP-кластер отказоустойчивым. [PostgreSQL standby](https://www.postgresql.org/docs/16/warm-standby.html).
