# Файлы, WebDAV и офисные редакторы

Реализация начиная с 0.9.16. Этот документ описывает файловый сервис Tayga; полная совместимость с API и приложениями Nextcloud не заявляется.

## Веб-интерфейс

В разделе «Файлы» доступны загрузка файлов и папок, перетаскивание, переименование и перемещение, скачивание папки ZIP, предпросмотр изображений и PDF, поиск по текущей папке и отдельный поиск по всему личному хранилищу. Список разбит на страницы по 50 элементов, поддерживает выбор и массовое перемещение в корзину.

Меню шестерёнки содержит «Корзина» и «Подключить WebDAV». У выбранного файла есть «История версий», а у офисных форматов — «Открыть в офисе». История и корзина доступны только владельцу: предоставление доступа к текущему документу не раскрывает его прежнее содержимое.

Перезапись из веба, публичной ссылки с правом записи, WebDAV или офиса сохраняет предыдущую версию. Незавершённая загрузка не заменяет текущий файл. Одновременное сохранение конфликтующих изменений отклоняется; клиент должен перечитать документ. Восстановление версии также сохраняет текущую версию. Восстановление из корзины не перезаписывает существующий файл на том же пути. Окончательное удаление из корзины требует подтверждения в интерфейсе.

При перемещении явные права доступа и публичные ссылки следуют за файлом. При удалении в корзину они отзываются: новый файл на старом пути не становится общедоступным. После восстановления доступ нужно предоставить заново. Права на родительскую общую папку продолжают действовать для её содержимого.

## Создание документов из шаблонов (5 ноября 2026)

Кнопка «Создать документ» открывает выбор шаблона и имени. Встроены пустой DOCX, протокол встречи DOCX с разделами, пустая XLSX с одним листом и PPTX с титульным слайдом. Если офисный сервер подключён, можно сразу открыть созданный файл; без него файл сохраняется для скачивания или последующего редактирования. Создание не зависит от доступности офисного сервера.

У поддерживаемого файла есть действие «Использовать как шаблон»: создаётся отдельная копия текущего содержимого. Поддержаны DOCX/XLSX/PPTX, ODT/ODS/ODP, RTF/TXT/CSV размером до 32 MiB. Это копирование документа, без преобразования формата, подстановки полей или исполнения макросов; DOTX/XLTX/POTX и общий управляемый каталог пользовательских шаблонов не реализованы. Содержимое, ссылки и прочие свойства выбранного пользовательского файла переносятся как есть. Встроенные файлы не содержат внешних связей и исполняемых объектов.

`GET /api/v1/files/templates` возвращает встроенный каталог и доступность офисного сервера. `POST` принимает directory/name и либо template_id, либо source_path/source_owner_id; owner_id задаёт владельца назначения, пустая строка явно выбирает личное хранилище. При отсутствии расширения добавляется расширение шаблона; другое расширение отклоняется. Папка назначения должна существовать. Совпадение имени возвращает 409 и не перезаписывает прежний файл. Повтор запроса после потери ответа с тем же именем тоже возвращает конфликт вместо второй копии.

Для пользовательской основы требуется чтение источника; для создания в общей папке — право записи самой папки. Читатель общего документа может сделать копию в личном хранилище. Исходник не меняется и его ACL/публичные ссылки не копируются. Перед публикацией повторно проверяются права и состояние пользователей, ETag источника, существование папки, блокировки и квота владельца. Сохранение использует тот же staging/commit, что веб, DAV и WOPI. При ошибке временный файл удаляется; параллельные запросы с одинаковым именем не перезаписывают друг друга.

API-тесты проверяют пакеты и XML встроенных файлов, отсутствие внешних связей, чтение через DAV и цикл созданного DOCX через WOPI с сохранением версии; копирование доступного источника, права общей папки/отзыв, неверные имена/форматы/пути, квоту, конкурентное создание и symlink. `node scripts/check-file-templates.mjs` проверяет форму в изолированном браузере, один POST при двойной отправке, копию общего файла в личную папку, конфликт, мобильную ширину и смену аккаунта. Встроенные пакеты повторно открыты python-docx/openpyxl/python-pptx; их регенерация — `scripts/build-file-templates.py`, Python не требуется серверу. Приёмка просмотра и редактирования всех форматов в рабочих Collabora/ONLYOFFICE/Р7 выполняется отдельно.

## Сравнение версий документов (5 ноября 2026)

В «Истории версий» у текстового документа доступна команда «Сравнить». Выберите исходную ревизию, текущий файл либо другую ревизию и режим. Доступ к истории остаётся только у владельца: ACL текущего общего файла не открывает прежнее содержимое. Сравниваются версии одного пути; чужие ID, другой файл, корзина и переходы каталогов отклоняются. Сравнение ничего не сохраняет и не блокирует рабочий файл.

**Текстовые изменения** доступны без офисного сервера для DOCX, ODT и UTF-8 TXT/MD/CSV. Показываются неизменённые, добавленные и удалённые строки/абзацы с номерами и знаками +/−. У офисных пакетов сравнивается основной текст, включая текст ячеек таблиц внутри документа, без оформления, изображений, колонтитулов, комментариев и примечаний. Архивные/служебные отличия ZIP не считаются изменениями текста; переводы строк нормализуются. Для ODT сохранены повторяющиеся пробелы, исключены аннотации и хранилище удалённого текста. Это не сравнение листов XLSX или слайдов PPTX. Ограничения: 32 MiB на файл, 8 MiB на XML тела, 1 MiB извлечённого текста и 2000 строк на сторону. Превышение и повреждённые/неподдерживаемые данные возвращают ошибку, без скрытого усечения.

**ONLYOFFICE/Р7** запускает сравнение DOCX/DOC/ODT/RTF/TXT в редакторе через `setRequestedDocument` с `c=compare`. Обе стороны передаются по отдельным read-only URL в пределах одной ограниченной сессии. Конфигурация редактора и параметры сравнения подписываются JWT; режим view, редактирование/review/скачивание/печать отключены, callback записи отсутствует. При недоступности метода в установленном редакторе показывается ошибка. Реальная доступность и качество отображения принимаются для конкретной версии/редакции ONLYOFFICE/Р7. Для электронных таблиц и презентаций добавлен отдельный структурный режим ниже; нативный Collabora остаётся расширением.

`POST /api/v1/files/library/compare` принимает path, left, right (`current` или ID ревизии), mode (`text`/`office`/`structured`/`details`/`visual`/`motion`) и lang. Текстовый ответ содержит строки и число добавлений/удалений, а также ETag прочитанных сторон. Обе стороны открываются под общей блокировкой; текстовый результат описывает этот снимок, даже если позднее рабочий файл изменён. Офисный ответ содержит URL просмотра с отдельным случайным токеном на 30 минут. До 32 активных сравнений на владельца, 1024 всего; состояние не переживает перезапуск и не создаёт копий на диске.

URL офисного сравнения даёт доступ только к двум выбранным версиям и не является токеном входа или редактирования. Каждый новый запрос проверяет аккаунт, срок сессии, текущие настройки провайдера/URL/секрета, существование и ETag обеих сторон. Изменение текущей стороны возвращает 409 и требует открыть сравнение заново; удалённая ревизия недоступна. Уже полученные данные не отзываются. URL содержит секрет доступа и не предназначен для пересылки. Все ответы сравнения имеют Cache-Control:no-store, браузер выводит текст через textContent.

`file_compare_test.go` проверяет текст/номера строк, пару исторических версий, DOCX/ODT, повторяющиеся пробелы и исключение комментариев, ограничения/повреждения, изоляцию истории, JWT и запрет записи, устаревшую текущую версию, удаление ревизии, истечение и смену секрета. `node scripts/check-file-comparison.mjs` проверяет интерфейс, экранирование содержимого, один запрос при двойной отправке, мобильную ширину, выбор разных версий, запуск офисного окна, конфликт и смену аккаунта. Нативная сторона проверяется контрактом API и браузерным тестом с подставленным ответом; фактический офисный движок отдельно не принимается этими тестами.

Протокол редактора: [ONLYOFFICE — Comparing documents](https://api.onlyoffice.com/docs/docs-api/samples/comparing-documents), [setRequestedDocument](https://api.onlyoffice.com/docs/docs-api/usage-api/methods/#setrequesteddocument).

### Сравнение таблиц и презентаций (5 ноября 2026)

Команда «История версий → Сравнить» поддерживает XLSX/ODS и PPTX/ODP без офисного сервера. Базовые режимы — «Листы и ячейки» и «Слайды и изображения»; для свойств оформления, диаграмм и анимации добавлен режим «Подробное сравнение», описанный ниже. Результат содержит только различия с карточками «Было / Стало», счётчиками добавленных/удалённых/изменённых записей и страницами по 100 карточек. Отсутствие различий означает совпадение сравниваемого содержимого, а не всех байтов или отрисовки файла.

**XLSX/ODS:** сопоставляются листы, их порядок/состояние, система дат и заполненные ячейки по координатам. Показываются типы/значения и выражения формул. Строки XLSX читаются через shared strings или inline strings; перестановка таблицы строк, номера групп shared formulas, изменение ZIP/путей изображений и числовая запись `1` вместо `1.0` не должны создавать ложных правок поддерживаемых данных. Общие формулы XLSX переводятся в выражения для конкретных ячеек с относительными/абсолютными ссылками A1, диапазонами строк/колонок, сохранением строковых литералов и имён листов. Формулы не исполняются, внешние книги не открываются, кеш формульных ячеек игнорируется. У XLSX учитываются явно заданные числовые форматы ячеек; прочие стили и форматирование ODS не сравниваются. Повторы ODS раскрываются только для заполненных значений; большие хвосты пустых строк/колонок пропускаются без разворачивания.

**PPTX/ODP:** слайды сопоставляются по ID/имени, взятым из структуры презентации, в объявленном порядке. Сравниваются позиция, имя/видимость, текст и использованные изображения. Изменение текста или изображения обнаруживается и без перестановки слайда; переименование файла изображения или служебного relationship ID при неизменённых данных не считается заменой. Изображения сравниваются по SHA-256 исходных байтов, без рендеринга: перекодирование того же изображения может быть отмечено как изменение. Интерфейс показывает число изображений и сокращённые отпечатки; это не просмотр изображений «до/после». Внешние изображения сравниваются по URL без сетевого запроса. Заметки, оформление/координаты объектов, диаграммы, аудио/видео, анимация, комментарии и макросы не сравниваются.

Режим API — `structured` в прежнем `POST /api/v1/files/library/compare`; для этих расширений он выбирается автоматически при отсутствии mode. Ответ содержит scope (`spreadsheet`/`presentation`), changes с section/group/address и before/after, счётчики added/removed/modified и ETag обеих сторон. Доступ только владельцу истории, другая версия должна принадлежать тому же пути. Файлы открываются под общей блокировкой и не изменяются. Контент выводится через textContent.

Ограничения на сторону: файл 32 MiB, до 10 000 записей сравнения и 2 MiB их данных, до 100 листов/500 слайдов. Разбор ограничен 512 прочитанными ZIP-частями, 16 MiB на часть, 32 MiB распакованных прочитанных данных, XML до 8 MiB/100 000 элементов/128 уровней. Координаты ограничены диапазоном A1:XFD1048576. Повреждения, дубли частей, выход relationship за пакет, переполнение и неподдерживаемые конструкции возвращают 422 без частичного результата. Формулы массивов/data tables XLSX, повторяемые формульные ячейки ODS, встроенные base64-изображения ODP и бинарные XLS/PPT пока не поддерживаются. Именованные стили ODS и скрытие через них не раскрываются; отображаемые числовые значения не форматируются офисным движком. Это сравнение сохранённых выражений и содержимого, а не доказательство математической эквивалентности формул.

`file_compare_structured_test.go` проверяет четыре формата, значения/формулы/адреса, shared strings и shared formulas против развёрнутой записи, пересчёт кеша без правок, повторения ODS, порядок/удаление слайдов, замену и переименование изображения, встроенные XLSX/PPTX, ограничения, неподдерживаемые формулы и изоляцию истории. Браузерная проверка `scripts/check-file-comparison.mjs` дополнена карточками таблиц/слайдов, экранированием, мобильной шириной и страницами результата. Приёмка большого набора реальных файлов разных офисных редакторов остаётся отдельно.

Форматы: [Open XML — shared strings](https://learn.microsoft.com/en-us/office/open-xml/spreadsheet/working-with-the-shared-string-table), [текст слайдов](https://learn.microsoft.com/en-us/office/open-xml/presentation/how-to-get-all-the-text-in-a-slide-in-a-presentation), [OpenDocument 1.3](https://docs.oasis-open.org/office/OpenDocument/v1.3/os/part3-schema/OpenDocument-v1.3-os-part3-schema.html).

### Визуальное сравнение страниц и слайдов (5 ноября 2026)

«История версий → Сравнить → Визуальное сравнение» показывает PDF, DOCX/DOC/ODT/RTF/TXT, XLSX/ODS и PPTX/ODP. PDF открывается без офисного сервера. Для остальных форматов нужен настроенный Collabora (включая провайдера по умолчанию), ONLYOFFICE или Р7 с доступным сервисом конвертации в PDF. Разрешение на конвертацию и доступность маршрута на стороне офисного сервера проверяются при развёртывании; отдельные логин и пароль пользователю не нужны. Оригиналы и история не изменяются.

Режимы: «Рядом» с подписями «Было / Стало», наложение с непрозрачностью 50% и разница пикселей с малиновой подсветкой. Страницы/слайды сопоставляются по номеру; вставленная страница не выравнивает последующие автоматически. Если страницы одной стороны нет, показывается белая область с явной подписью. Обе стороны растеризуются с одним масштабом в общий холст, поэтому различия размеров бумаги сохраняются. На телефоне стороны расположены друг под другом. Навигация не запускает повторную конвертацию.

PDF.js отрисовывает только выбранную пару, без выполнения JavaScript документа и интерактивных аннотаций. Разрешение ограничено 1800 пикселями по каждой стороне и примерно 2 млн пикселей на холст; процент различий считается по всему этому холсту с порогом максимальной разницы RGB > 24/255. Это сравнение статичной отрисовки, а не процент смысловых изменений или доказательство идентичности исходников. Мелкие детали ниже выбранного разрешения/порога могут не попасть в подсветку. Движок и установленные на офисном сервере шрифты влияют на результат, таблицы используют печатную разметку сервера; формулы могут пересчитываться самим офисным движком. В статичном режиме анимация/переходы не воспроизводятся. Для поддерживаемых эффектов PPTX/ODP есть отдельный режим «Кадры и анимация», описанный ниже.

API: `POST /api/v1/files/library/compare` с `mode:"visual"` возвращает `left_url`/`right_url` под `/office/compare/pdf`. История доступна владельцу, не получателям общей папки. Отдельный токен ограничен парой версий, 30 минутами и текущей конфигурацией офиса; не является токеном входа, редактирования или WOPI. Проверяются включённая учётная запись, существование и ETag обеих версий до и после конвертации; изменение текущего файла даёт 409, удаление ревизии — 404, отзыв конфигурации/истечение — 401. Ответы `no-store`; при закрытии окна отменяются загрузки/отрисовка и освобождаются PDF.js worker, при смене аккаунта окно закрывается. Уже полученные байты отозвать невозможно.

ONLYOFFICE/Р7 получает подписанный JWT запрос `/converter` с `async:false` и ссылкой на выбранный исходник. Выходной URL допускается только на том же HTTPS-хосте/порту, редиректы отключены. Collabora получает ограниченный multipart поток снимка файла в `/cool/convert-to/pdf`, без публичного исходного URL. PDF не сохраняются на диске Tayga: только память запроса и открытого окна. Офисный сервер может иметь собственный кэш, управляемый его настройками. Ограничения: исходник и каждый PDF до 32 МиБ, до 500 страниц на версию в просмотре, до четырёх конвертаций одновременно на процесс, 90 секунд на запрос; при занятости 429. Лимиты сессий общие с нативным сравнением: 32 на владельца / 1024 на процесс. Ошибки конвертации не раскрывают URL, JWT или исходное тело ответа провайдера.

Проверки: `file_compare_render_test.go` проверяет изоляцию владельцев, отзыв версий, запрет записи, PDF-сигнатуру, JWT ONLYOFFICE/Р7, multipart Collabora, запрет чужого хоста и редиректов, смену исходника во время конвертации. `node scripts/check-file-rendered-comparison.mjs` использует настоящий PDF.js с контролируемыми PDF и проверяет пиксельную разницу, наложение, общий масштаб, навигацию, отсутствующую страницу, мобильную ширину и закрытие. Серверы конвертации в Go-тестах подставлены TLS-стендом: приёмка реальных офисных серверов и шрифтов остаётся отдельной.

### Сравнение кадров и воспроизведение эффектов (5 ноября 2026)

Для PPTX/ODP выберите «История версий → Сравнить → Кадры и анимация». Нужен настроенный Collabora, ONLYOFFICE или Р7 с PDF-конвертацией. Две версии воспроизводятся на общей шкале в миллисекундах; доступны «Воспроизвести / Пауза», перемотка, шаг ±40 мс, выбор слайда, «Рядом», наложение 50% и подсветка разницы кадров. Воспроизводится выбранный слайд; его переход использует конечное состояние предыдущего, а первый слайд появляется из белого поля. Начальные состояния, конечные состояния и все промежуточные моменты можно сравнивать отдельно.

**Поддерживаемый набор:** появление/исчезновение целого объекта и линейное затухание входа/выхода; последовательные эффекты по щелчку и после предыдущего, параллельные «с предыдущим», объектные click-триггеры и ограниченные траектории движения (см. расширение ниже), числовая задержка и длительность до 30 с. Переходы — cut, fade, направленные wipe и push (в ODP — поддерживаемые варианты barWipe/pushWipe). Для PPTX без явной длительности перехода используются 500/1000/2000 мс по fast/med/slow; для ODP — 1000 мс. В предпросмотре щелчки моделируются автоматически: пауза 500 мс перед следующим эффектом по щелчку после завершения предыдущего эффекта. Это заданный порядок воспроизведения для сравнения; реальные интервалы действий докладчика в файле не сохраняются. Смена длительности в одной версии сдвигает её дальнейшие эффекты на общей шкале.

Сервер разбирает временную шкалу, готовит отдельную временную презентацию с ключевыми состояниями и убирает из неё анимацию/переходы. На начальном кадре входящие объекты отсутствуют; последующие состояния последовательно показывают/убирают соответствующий объект. Слайды, текст, изображения, диаграммы и оформление этих состояний отрисовывает настроенный офисный движок в PDF. Браузер получает проверенный набор PDF-страниц и выполняет заданные композиции между состояниями либо отдельными слоями объектов, без запуска кода, макросов, SVG-скриптов или JavaScript исходного документа. Это ограниченный проигрыватель поддерживаемых эффектов, а не полная эмуляция PowerPoint/Impress. Синтетические слайды могут повлиять на пересчёт офисным движком динамических полей номера страницы/количества слайдов/дат; такие поля и шрифты требуют отдельной визуальной приёмки. Расхождение числа PDF-страниц с числом состояний блокирует воспроизведение: неподходящий конвертер или пропуск скрытых слайдов не должны сдвинуть соответствие кадров незаметно.

Неподдерживаемые эффекты дают явное предупреждение на соответствующем слайде. Весь такой слайд остаётся статичным, без перехода; его объекты показываются в сохранённом статичном виде. В частности, не исполняются mouseover/keyboard/media-триггеры, многократные интерактивные последовательности, эффекты частей текста и объектов внутри групп, неподдерживаемые варианты траекторий, неподдерживаемые варианты вращения/масштаба/цвета, повторение, ускорение/замедление, мультимедиа, звук переходов, произвольные фильтры, legacy-анимация ODP и наследуемые стили переходов ODP. Набор можно расширять отдельно, не выдавая неподдерживаемое поведение за точное воспроизведение. На слайдах с предупреждением сравнивается только доступная статичная отрисовка.

API `mode:"motion"` возвращает `left_timeline`/`right_timeline` (`/office/compare/timeline`) и `left_url`/`right_url` (`/office/compare/pdf?...&storyboard=1`). Временная шкала содержит номера PDF-состояний, эффекты, длительности, переходы и предупреждения. Подготовленный источник для ONLYOFFICE/Р7 доступен исключительно под токеном этого режима с `storyboard=1`; обычный токен визуального/нативного сравнения не открывает шкалу или подготовленную презентацию, а токен motion не открывает редактор/сохранение. Владельцы, срок токена, настройки и ETag обеих версий проверяются до работы и повторно перед выдачей результата; PDF-конвертация проверяет их также после сетевого запроса. Исходники, история и квоты записи не изменяются.

Лимиты: 1–50 слайдов, 12 эффектов на слайд, 120 ключевых состояний на версию, 32 МиБ исходник/подготовленный ZIP/PDF, 32 МиБ суммарного генерируемого XML и 64 МиБ распакованного содержимого подготовленного пакета. Не более двух сборок состояний и четырёх PDF-конвертаций одновременно на процесс; занятость возвращает 429. Синтезированный PPTX/ODP временно записывается в файл с правами 0600 и удаляется после обработки запроса; это не новая версия в библиотеке. Кэш конвертации офисного сервера управляется отдельно. Срок токена и ограничения числа сессий общие с визуальным режимом.

PDF.js кэширует растры только выбранного слайда и предыдущего конечного состояния, в общем масштабе, до примерно 400 тыс. пикселей на кадр и до 1000 пикселей по каждой стороне. Изображение разницы использует порог RGB > 24/255; маленькие детали могут не попасть в подсветку. Воспроизведение перерисовывается примерно 12,5 раза в секунду, точка ручной перемотки задаётся отдельно. Пауза не запускает повторную конвертацию. Закрытие/смена аккаунта отменяют загрузки, отрисовку и таймеры, освобождают worker; скрытие вкладки останавливает воспроизведение. Уже полученные байты отозвать невозможно.

Проверки: `go test ./internal/httpapi -run TestMotion`, `node scripts/check-file-motion.mjs` (настоящая отрисовка PDF.js, разные длительности, переход, кадры, пауза, перемотка, XSS предупреждений, мобильная ширина, смена аккаунта). Дополнительная локальная приёмка: `TAYGA_TEST_OFFICE_RENDER=1 go test ./internal/httpapi -run TestMotionRealOfficeRendering -v`, требует LibreOffice и Poppler. Она подготавливает PPTX и экспортированный LibreOffice ODP, отрисовывает по два состояния и проверяет различающиеся пиксели. В этой среде оба формата прошли такую проверку; приёмка настроенных рабочих Collabora/ONLYOFFICE/Р7 и конкретных шрифтов остаётся отдельной.

Схемы эффектов: [Microsoft — AnimateEffect](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.presentation.animateeffect), [OASIS — OpenDocument 1.3, Part 3](https://docs.oasis-open.org/office/OpenDocument/v1.3/os/part3-schema/OpenDocument-v1.3-os-part3-schema.pdf).

#### Параллельные эффекты, объектные триггеры и траектории (5 ноября 2026)

Режим «Кадры и анимация» расширен для PPTX и ODP. «С предыдущим» начинает эффект одновременно с предыдущим стартом с учётом собственной задержки; «после предыдущего» — после предыдущего окончания. Следующий обычный щелчок по-прежнему моделируется спустя 500 мс после завершения группы. Разные объекты могут одновременно появляться, исчезать и двигаться; прозрачность и смещение одного объекта также могут меняться одновременно. Перекрывающиеся эффекты одной и той же характеристики объекта (например, два параллельных изменения прозрачности) дают предупреждение и статичный слайд, поскольку такой конфликт нельзя достоверно разрешить текущей моделью.

**Интерактивность:** PPTX `interactiveSeq`/`onClick` с целью `spTgt`, ODP `id.click` и `id.click+delay`. Эффект запускается в текущий момент общей шкалы щелчком на прямоугольной области объекта в режиме «Рядом» или доступной с клавиатуры кнопкой «Триггер». Для объекта без явной геометрии остаётся кнопка. Парные триггеры сопоставляются по порядку объектов в двух версиях, названия обеих сторон видны на кнопке; это не автоматическое доказательство идентичности объектов после структурного редактирования. Скрытый анимацией объект не принимает щелчок. Поддерживаются один запуск каждой интерактивной последовательности на слайд и совместное выполнение независимых триггеров. Повторный запуск требует «Сбросить триггеры»: он очищает историю и возвращает время к нулю. Несколько стадий, требующих повторных щелчков внутри одной интерактивной последовательности, пока не поддерживаются.

Время запуска сохраняется в памяти открытого окна для каждой версии. Перемотка назад и вперёд воспроизводит ту же историю событий, а не создаёт новые щелчки. Смена слайда, сброс, закрытие или смена аккаунта очищают историю. Таймеры и воспроизведение по-прежнему останавливаются при закрытии/скрытии окна. В конце основной временной шкалы можно запустить ещё не активированный триггер; шкала расширится по его длительности.

**Движение:** нормированные относительно размеров слайда пути с началом в исходном положении объекта (`M 0 0`), команды M/L/C/Z и конечный E для PPTX, абсолютные и относительные M/L/C/Z для ODP. Кривые Безье разбиваются на 24 участка; движение идёт с постоянной скоростью по длине полученной ломаной, без автоматического разворота объекта. Поддержана одна траектория на объект. Путь ограничен 8192 символами, 2048 токенами и 512 точками; исходные числа — до ±4 размера слайда, накопленные координаты — до ±16. Дуги, произвольные SVG-команды, несколько подпутей, начальное смещение от `M 0 0`, специальные системы координат, автоматический разворот вдоль пути, повторение и нелинейная скорость отклоняются с предупреждением. Для движения требуется явная геометрия объекта с исходным прямоугольником целиком внутри слайда; унаследованная геометрия и трансформированные объекты ODP остаются статичными. Исходный SVG/XML не исполняется: браузер получает только проверенные числовые точки.

**Слои:** офисный сервер отдельно отрисовывает исходный фон/мастер и упорядоченные слои локальных объектов. Для каждого слоя готовятся чёрная и белая подложки; разница этих двух растров позволяет восстановить прозрачность. Поэтому перемещается только объект, а фон, соседние объекты и порядок перекрытия сохраняются. Статичные объекты без ID получают внутренние уникальные ключи и не дублируются между слоями. Две контрольные пустые страницы проверяют, что конвертер сохранил подложки; при провале проверки воспроизведение останавливается с понятной ошибкой, а непрозрачный прямоугольник не выдаётся за слой.

Общий лимит 120 PDF-страниц теперь включает ключевые состояния, фон, контрольные подложки и пары слоёв; на сложной презентации он достигается раньше. До 25 слоёв на слайд; разрешение расширенного режима ограничено примерно 150 тыс. пикселей на кадр, чтобы ограничить память растров. Последовательный режим сохраняет прежний предел 400 тыс. пикселей. Прежние ограничения размера ZIP/XML/PDF, параллелизма, доступа и отзыва сессий остаются в силе. Маттирование и растровая композиция — приближение; качество краёв, теней, динамических полей и шрифтов проверяется на используемом офисном сервере.

Проверки: `file_compare_motion_layers_test.go` проверяет разбор путей, параллельную/интерактивную шкалу, маттирование, сохранение порядка безымянных объектов и отказ при конфликте одной характеристики. `node scripts/check-file-motion-layers.mjs` использует настоящий PDF.js и проверяет одновременные затухания, щелчок на объекте, движение без сдвига фона, историю/сброс событий, разные ID между версиями, разницу кадров, мобильную ширину и очистку при смене аккаунта. `TAYGA_TEST_OFFICE_RENDER=1 go test ./internal/httpapi -run TestMotionAdvancedRealOfficeLayers -v` проверяет подготовленные PPTX и экспортированный LibreOffice ODP на настоящей конвертации, включая чёрные/белые контрольные страницы. Оба формата прошли локальную приёмку; настроенные рабочие офисные серверы по-прежнему требуют отдельной проверки.

Схемы: [Microsoft — AnimateMotion](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.presentation.animatemotion), [OASIS — OpenDocument 1.3, Part 3](https://docs.oasis-open.org/office/OpenDocument/v1.3/os/part3-schema/OpenDocument-v1.3-os-part3-schema.pdf).

#### Вращение, масштабирование и RGB-заливка (5 ноября 2026)

В «Кадры и анимация» добавлены вращение и масштаб целого объекта, а также изменение его сплошной RGB-заливки. Эти эффекты используют ту же шкалу времени, паузу/перемотку, сравнение кадров, параллельное выполнение и click-триггеры. Вращение, масштаб, движение, заливка и затухание могут идти одновременно у одного объекта; два изменения одной характеристики остаются неподдерживаемым конфликтом. Допускается один эффект каждого вида на объект в пределах слайда.

**PPTX:** поддержаны `animRot` (относительное `by` либо нулевое `from` и `to`, угол в 1/60000 градуса), `animScale` (100000 соответствует исходному размеру, `by`/`to` с исходным масштабом 100%) и `animClr` для `fillcolor` в пространстве RGB. Для вращения принят диапазон до ±3600°, для каждой оси масштаба — от 0,01 до 8. Цвет задаётся явным sRGB `RRGGBB`; начальный цвет выводится из исходной заливки, если `from` не указан, и должен соответствовать этой заливке. Поддерживаются простые фигуры с явно заданной сплошной RGB-заливкой. Цвета темы, HSL, градиенты и отдельный цвет текста/контура расширены следующим этапом ниже. Относительные цвета добавлены отдельным этапом ниже; изображения как цветовые цели и неподдерживаемые цветовые модификаторы остаются расширением.

**ODP:** поддержаны emphasis-эффекты `animateTransform` с типами rotate/scale и `animateColor` для `fill-color`. Относительный `by` масштаба задаёт прибавку: `0.5,-0.5` превращается в 150% × 50%, тогда как вращение `by="90"` задаёт 90°. Можно также задать конечное значение при начальных 0°/100%. Дополнительные точки вращения, отрицательный/нулевой масштаб, сложные формулы, keyTimes/keySplines и последовательности values не исполняются. Для цвета принимаются `#RRGGBB`, RGB и линейный либо дискретный режим; при отсутствии calcMode используется стандартное для ODF дискретное изменение (переход между двумя значениями посередине интервала). Вращение/масштаб воспроизводятся линейно. Исходная сплошная заливка определяется по графическому стилю; неподдерживаемое описание даёт предупреждение и статичный слайд.

Офисный сервер отрисовывает дополнительные чёрные/белые пары для исходной и конечной заливки. Меняется свойство заливки в временной копии стиля/фигуры, а не оттенок всех пикселей: текст, контур, их цвета и оформление сохраняются. В ODP копируются исходные графические и, при наличии переопределения заливки, абзацные стили — без изменения общих стилей других состояний. Промежуточный цвет собирается из этих растров с сохранением прозрачности.

Композиция вращает и масштабирует растровый слой относительно центра исходного прямоугольника, сохраняя фон и порядок перекрытия. Учитывается исходный угол PPTX. Проверка щелчка использует обратное преобразование, поэтому триггер остаётся доступен после вращения/масштабирования. Требуется явная поддерживаемая геометрия; ограничения исходного положения и трансформированных объектов ODP прежние. Масштаб растягивает весь объект, включая его содержимое, а не повторно набирает текст или перестраивает диаграмму. Конечная поза для перехода к следующему слайду собирается из слоёв, включая конечные углы, масштаб и цвет; интерактивная история при смене слайда очищается.

API расширен параметрами `from`/`to`, флагом дискретного цвета, ссылками `colors` на дополнительные пары PDF-страниц и исходным углом в геометрии. Цветовые пары входят в общий предел 120 страниц; суммарный генерируемый XML, включая скопированные стили, ограничен 32 МиБ. Лимиты размера PDF, разрешения, количества эффектов и параллелизма не увеличены. Новых прав или токенов редактирования нет; исходники и история не меняются.

Проверки: `file_compare_motion_transform_test.go` проверяет единицы/диапазоны, RGB-маски, сохранение текста/контура и отказ при неподдерживаемых значениях. `node scripts/check-file-motion-transform.mjs` использует настоящий PDF.js: совместное вращение/масштаб, промежуточный цвет, сохранение чёрных деталей, щелчок после преобразования, конечную позу предыдущего слайда в переходе, разницу кадров и мобильную ширину. `TAYGA_TEST_OFFICE_RENDER=1 go test ./internal/httpapi -run TestMotionTransformRealOfficePalettes -v` проверяет PPTX и экспортированный LibreOffice ODP: разбор вращения/масштаба и фактическую отрисовку исходной красной/изменённой синей заливки. #### Цвета темы, HSL, градиенты, текст и контур (5 ноября 2026)

В «Кадры и анимация» добавлены цвета темы PPTX, HSL-интерполяция и независимые цветовые эффекты заливки, текста и контура для PPTX/ODP. Разные характеристики одного объекта могут меняться одновременно: они складываются как изменения предварительно умноженных на прозрачность цветовых слоёв. Изменение текста не перекрашивает заливку/контур; изменение контура не заменяет текст. Для одного свойства по-прежнему допускается один эффект на слайд, а неподдерживаемый конфликт даёт предупреждение и статичный слайд.

**PPTX:** распознаются `fillcolor`, `stroke.color` и `style.color`. Цвета темы разрешаются по локальной цепочке слайд → макет → мастер → тема, включая themeOverride и clrMap/clrMapOvr; masterClrMapping возвращает карту мастера. Поддержаны sRGB, DrawingML HSL, schemeClr и sysClr с lastClr, а также ограниченный набор tint/shade/lumMod/lumOff/satMod/satOff. Прозрачные цветовые модификаторы и неизвестные преобразования отклоняются. Разрешение темы не выполняет сетевых запросов; внешняя зависимость темы даёт предупреждение. Для текста учитываются явно заданные цвета run, defRPr и fontRef/tx1. Поддерживаются весь текст объекта и pRg, охватывающий все его абзацы; частичные диапазоны остаются неподдерживаемыми. В качестве начального цвета при отсутствии from используется сохранённое оформление объекта, как и в прежнем ограниченном проигрывателе; это не полная эмуляция всех значений по умолчанию PowerPoint.

**HSL:** поддержаны clockwise/counter-clockwise, включая корректное прохождение через 0° и обработку ахроматических цветов. Оттенок меняется в заданном направлении, насыщенность и светлота — линейно. Непрерывное HSL представлено девятью отрисованными цветными состояниями; между соседними состояниями смешиваются растры. Это аппроксимация, а не обещание точного совпадения каждого кадра офисного движка. Для RGB достаточно исходного и конечного состояния. Дискретный режим ODP сохраняется; при отсутствии calcMode действует прежнее дискретное изменение, поэтому сам по себе HSL не превращает его в плавный эффект. В ODP поддержаны fill-color, stroke-color и color (цвет текста в используемой модели Impress); разрешённые направления нормализуются в cw/ccw. Цвета темы в ODP используются в виде уже разрешённых значений стилей, отдельные нестандартные ссылки на тему не исполняются.

**Градиенты:** сохраняются геометрия, угол, позиции цветовых остановок и порядок исходного градиента. В цветовых эффектах начальная палитра берётся из остановок; каждая из них интерполируется к конечному цвету. На последнем кадре остановки совпадают по цвету, но описание градиента остаётся. Анимация угла и радиального фокуса PPTX добавлена следующим этапом ниже; позиции остановок остаются фиксированными. Для PPTX принимаются явно заданные gradFill с 2–16 упорядоченными остановками; для ODP — стандартные двухцветные draw:gradient и RGB gradient-stop, используемые LibreOffice, до 16 остановок. Копии именованных градиентов и стилей относятся только к временным состояниям и не меняют общие определения исходника. Фиксированные координаты градиента PPTX (rotWithShape=0), неизвестные виды остановок, частичная прозрачность цвета и неподдерживаемое наследование дают предупреждение. Градиент также сохраняется, когда анимируется только текст или контур.

Офисный сервер отрисовывает каждое цветовое состояние с чёрной/белой подложкой. В браузер передаются только проверенные ссылки на PDF-страницы и числовые параметры, без исполнения XML/SVG/кода документа. Подготовленные состояния текста сохраняют шрифт, размер, разбиение на run и другие свойства; в ODP копируются только нужные графические/абзацные/текстовые стили. Одновременное изменение нескольких свойств, края, тени, необычное наследование и динамические поля требуют визуальной приёмки на рабочем офисном сервере.

Для обычной палитры API `colors[].samples` содержит пары страниц и положение каждого из максимум девяти цветовых состояний (совместные сетки расширены ниже); прежние from_black/from_white/to_black/to_white сохраняют ссылки на крайние состояния. В эффекте указываются property, space и direction. Для градиента/разноцветного текста from — представитель исходной палитры; сами PDF-состояния сохраняют полное оформление. Все дополнительные страницы входят в прежний лимит 120 страниц на версию. Ограничения: 1024 текстовых run, 32 ссылки на стили одного цветового объекта, 8 МиБ создаваемых цветовых стилей за состояние; прежние ограничения XML/ZIP/PDF и параллелизма действуют без увеличения. Повреждённый пакет или превышение лимита останавливают подготовку с ошибкой; неподдерживаемое описание эффекта оставляет слайд статичным с предупреждением.

Проверки: `file_compare_motion_color_test.go` проверяет разрешение темы/карты цветов, HSL в обоих направлениях, tint, градиентные остановки, независимые свойства и объявления пространств имён. `node scripts/check-file-motion-color.mjs` использует настоящий PDF.js: различие HSL и RGB в середине градиента, одновременные заливка/текст/контур, точные конечные цвета, подсветка кадров, мобильная ширина и закрытие при смене аккаунта. `TAYGA_TEST_OFFICE_RENDER=1 go test ./internal/httpapi -run TestMotionRichColorRealOffice -v` проверяет настоящую конвертацию PPTX и экспортированного LibreOffice ODP, изменение всех трёх свойств и конечный цвет градиента. Оба формата прошли локальную проверку; реальные Collabora/ONLYOFFICE/Р7 проверяются отдельно.

Схемы: [Microsoft — AnimateColor](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.presentation.animatecolor), [ограничения attrNameLst](https://learn.microsoft.com/en-us/openspecs/office_standards/ms-oe376/625cf947-1313-4aef-ae37-a2f746b379b3), [Tint](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.tint), [OASIS — OpenDocument 1.3, Part 3](https://docs.oasis-open.org/office/OpenDocument/v1.3/os/part3-schema/OpenDocument-v1.3-os-part3-schema.pdf).

#### Относительные цвета и геометрия градиентов (5 ноября 2026)

В «Кадры и анимация» добавлены относительные цветовые эффекты PPTX/ODP и ограниченная анимация геометрии градиентов PPTX. Они используют общую шкалу времени, слои, триггеры, сравнение кадров и конечные состояния переходов. Исходные файлы не изменяются.

**Относительные цвета:** `animClr/by` PPTX принимает подписанные компоненты `p:rgb` (±100000 соответствует ±255 каналов RGB) или `p:hsl` (оттенок в 1/60000 градуса, насыщенность/светлота в долях 100000). Пространство операнда должно совпадать с clrSpc. ODP `animateColor` принимает `by` в виде `#RRGGBB`, `rgb(r,g,b)` с каналами ±255 или ±100%, либо `hsl(h,s%,l%)` с оттенком ±360° и насыщенностью/светлотой ±100%. При наличии `to` используется оно, а `by` игнорируется. Как и прежде, исходный цвет берётся из сохранённого оформления; явно заданный `from` должен ему соответствовать. Разность применяется отдельно к каждой остановке градиента и каждому поддерживаемому цвету текста/контура. RGB, насыщенность и светлота ограничиваются допустимыми значениями на каждом промежуточном шаге; оттенок оборачивается по кругу. Знак приращения задаёт направление относительного оттенка. Полный оборот 360° сохраняет промежуточные цвета даже при одинаковых начальном и конечном цветах.

**Геометрия PPTX:** числовой `p:anim` с `valueType="num"` поддерживает `fill.angle`, `fill.focusposition.x` и `fill.focusposition.y`, операнды `from/to/by`, линейный или дискретный режим. Угол задаётся в градусах против часовой стрелки; допустимый размах — до одного оборота. Он переводится в DrawingML без изменения положения фигуры, текста, контура и цветовых остановок. При отсутствии ang исходный линейный угол равен нулю. Для радиального градиента circle/rect положение центра фокуса нормировано в диапазон 0–1; размер исходного fillToRect сохраняется, весь фокусный прямоугольник должен оставаться внутри заливки. Требуется явно заданный gradFill простой фигуры с 2–16 остановками. Фиксированные координаты rotWithShape=0 и неподдерживаемое наследование дают статичный слайд с предупреждением.

Для непрерывного относительного цвета и геометрии подготавливаются девять растровых состояний, для дискретного — два. Браузер смешивает соседние состояния: это ограниченная аппроксимация, особенно для вращающихся градиентов, а не точное вычисление каждого кадра Office. Все страницы входят в прежний предел 120 страниц на версию; ограничения XML/ZIP/PDF, авторизации и параллельной конвертации сохранены. API эффекта содержит `relative`, `delta`, `delta_space`; геометрия имеет kind=`gradient`, property=`angle`/`focus-x`/`focus-y` и использует прежний массив `colors[].samples`. Формулы, скрипты и произвольные атрибуты из документа не исполняются.

**Границы:** допускается один эффект геометрии градиента на объект. Совместная геометрия и цвет заливки добавлены следующим этапом ниже; независимые текст/контур также могут анимироваться вместе с геометрией. Геометрия ODP добавлена профилем Tayga ниже. Размер фокуса PPTX и позиции остановок добавлены ниже; keyframes/tavLst и нелинейные режимы остаются открытыми. Неизвестные или повреждённые параметры не подменяются похожим эффектом.

Проверки: `file_compare_motion_relative_test.go` покрывает полный оборот оттенка, ограничение RGB на промежуточном шаге, приоритет to, допустимый синтаксис ODP, направление угла, радиальный фокус и отказ на формулах/нечисловых значениях/неподдерживаемой геометрии. `node scripts/check-file-motion-relative-gradient.mjs` использует настоящий PDF.js с тестовыми PDF: цикл оттенка с совпадающими концами, вращение градиента, сохранение фона, разницу кадров, смену слайда, мобильную ширину и очистку при смене аккаунта. `TAYGA_TEST_OFFICE_RENDER=1 go test ./internal/httpapi -run TestMotionRelativeAndGradientRealOffice -v` проверяет отличающиеся начальный/конечный растры через локальные LibreOffice/Poppler для относительного цвета PPTX/ODP и угла/фокуса PPTX. Это не проверка точности импорта анимации между форматами: LibreOffice при экспорте PPTX в ODP может менять числовую запись относительного оттенка. Рабочие Collabora/ONLYOFFICE/Р7 требуют отдельной визуальной приёмки.

#### Геометрия ODP и совместная анимация заливки (5 ноября 2026)

В «Кадры и анимация» добавлены геометрия градиентов ODP по профилю Tayga и совместная отрисовка геометрии/цвета заливки для PPTX и ODP. Цвет и геометрия имеют независимые часы: можно задавать разные длительности, задержки и поддерживаемые триггеры, перематывать кадры и сравнивать версии. Один объект по-прежнему может иметь только один эффект геометрии и один эффект цвета заливки; текст/контур остаются отдельными свойствами.

**Совместная отрисовка:** офисный движок получает комбинации фаз цвета и геометрии, а не два независимых изменения исходного растра. Браузер выбирает четыре соседних состояния и смешивает их с предварительным умножением на прозрачность. Это сохраняет взаимодействие цвета с направлением/центром градиента, в том числе когда один эффект ещё не запущен или уже завершён. Для обычного непрерывного RGB используются 2 фазы цвета × 9 геометрии (18 пар чёрного/белого фона). Для HSL/относительного цвета — 9 × 5 (45 пар); для дискретной оси достаточно двух фаз. Смешивание растров остаётся аппроксимацией, особенно для полного оборота и быстро меняющейся геометрии. API совместной палитры содержит `geometry_effect` — индекс второго эффекта, а образцы `samples` содержат `at` (цвет) и `geometry_at` (геометрия). Нулевая geometry_at может быть опущена. Клиент проверяет прямоугольную сетку, порядок, обе границы, диапазоны и совпадение целей; повреждённая сетка останавливает просмотр.

**Профиль ODP:** стандартный список smil:attributeName не определяет геометрию градиента. Поэтому следующие буквальные значения являются расширением проигрывателя Tayga, а не штатными эффектами Impress: `tayga:gradient-angle`, `tayga:gradient-center-x`, `tayga:gradient-center-y`. Они используются в `anim:animate` внутри существующей emphasis-последовательности; smil:targetElement указывает ID фигуры, из её графического стиля разрешается ссылка на draw:gradient. Пример эффекта угла:

```xml
<anim:par presentation:node-type="on-click" presentation:preset-class="emphasis">
  <anim:animate smil:attributeName="tayga:gradient-angle"
    smil:targetElement="shape" smil:dur="1s" smil:from="0" smil:to="90"/>
</anim:par>
```

Используются обычные пространства имён ODF для anim/smil/presentation; `tayga:` здесь — часть документированного строкового имени свойства, а не XML-атрибут. Поддержаны `from/to/by` (to имеет приоритет), `linear` по умолчанию и `discrete`. Угол в профиле задаётся в градусах, максимальный размах 360°; начальный draw:angle читается в десятых долях градуса либо с суффиксом deg. Центр задаётся числами 0–1, исходные draw:cx/cy — процентами (по умолчанию 50%). Угол доступен для linear/axial, центр — radial/ellipsoid/square/rectangular. Явный from должен совпадать с сохранённым значением. Центр остаётся внутри 0–1; неизвестные свойства, формулы, values/keyTimes/keySplines, нелинейные и повторяемые режимы дают статичный слайд с предупреждением. Имена свойств fill.angle/draw:angle не считаются неявными синонимами профиля.

Для каждого состояния копируются только нужные определения градиента и графические/абзацные стили; общие именованные градиенты и другие фигуры не изменяются. Сохраняются цветовые остановки, текст и контур. Исходник остаётся неизменным; профиль не обещает воспроизведение этих эффектов или их сохранение после редактирования в Impress. Конвертеру передаются уже подготовленные статические состояния, поэтому он не должен исполнять расширение анимации.

Прежние пределы остаются: 120 PDF-страниц на версию, 12 эффектов на слайд, 16 остановок, 32 ссылки на стили объекта, 8 МиБ добавленных цветовых стилей за состояние, ограничения общего XML/ZIP/PDF и параллелизма. Совместная сетка расходует больше страниц; превышение лимита явно останавливает подготовку. Размер фокуса PPTX и позиции остановок добавлены следующим этапом ниже. Несколько эффектов геометрии на объект и обмен расширенными эффектами ODP с другими редакторами остаются отдельными задачами.

Проверки: `file_compare_motion_joint_test.go` проверяет обе оси сетки, RGB/HSL, сохранение исходного градиента, угол/центр ODP, дискретный режим и отказ на недопустимых значениях/формулах/неподдерживаемых именах. `node scripts/check-file-motion-joint-gradient.mjs` использует настоящий PDF.js: разные задержки двух эффектов, конечный цвет, перемотку, сравнение кадров, навигацию, мобильную ширину, очистку при смене аккаунта и отказ на неполной сетке. `TAYGA_TEST_OFFICE_RENDER=1 go test ./internal/httpapi -run TestMotionJointGradientRealOffice -v` проверяет реальные растры PPTX/ODP через LibreOffice/Poppler: угол/центр ODP и комбинации цвета/геометрии обоих форматов. Это проверка отрисовки подготовленных состояний, а не нативной анимации расширения в Impress; рабочие офисные серверы требуют отдельной приёмки.

Основание профиля: [OASIS — smil:attributeName и стандартный список свойств](https://docs.oasis-open.org/office/OpenDocument/v1.4/csd01/part3-schema/OpenDocument-v1.4-csd01-part3-schema.html), [OpenDocument 1.3, Part 3](https://docs.oasis-open.org/office/OpenDocument/v1.3/os/part3-schema/OpenDocument-v1.3-os-part3-schema.pdf).

#### Размер фокуса и позиции остановок (5 ноября 2026)

В «Кадры и анимация» добавлены ширина/высота фокуса PPTX и перемещение цветовых остановок PPTX/ODP. Эти эффекты используют прежнюю геометрическую ось палитры и совместные состояния с цветом заливки; перемотка, дискретный режим, поддерживаемые триггеры и конечная поза переходов сохраняются. Исходники не изменяются.

**Размер фокуса PPTX:** числовой `p:anim valueType="num"` распознаёт `fill.focussize.x` и `fill.focussize.y` с `from/to/by`; 0–1 соответствует размеру относительно ширины/высоты заливки. Начальный размер выводится из fillToRect, центр и другая ось сохраняются. Конечный фокусный прямоугольник должен целиком оставаться внутри заливки. Поддержаны path=rect и центрированный path=circle, явная геометрия и разрешимые непрозрачные цвета/остановки; tileRect, flip градиента и смещённый круговой фокус дают предупреждение. Расширение одной оси — один геометрический эффект; одновременные независимые изменения двух осей пока не объединяются. Размер фокуса ODP не подменяется параметром draw:border: он остаётся отдельным расширением, поскольку стандартный draw:gradient не содержит эквивалента фокусного прямоугольника DrawingML.

LibreOffice при импорте fillToRect использует центр и теряет размер. Чтобы проигрывание работало и через такой конвертер, для каждого состояния размера фокуса формируется только заливка в PNG 256×256. Эта заливка устанавливается в копии фигуры; текст, контур, исходная геометрия/поворот, маски и фон продолжают отрисовываться офисным движком. Все исходные и промежуточные состояния данного эффекта используют одинаковый способ подготовки. Прямоугольный фокус интерполируется вложенными прямоугольниками, центрированный круговой — вложенными эллипсами; это ограниченная растровая аппроксимация, без гарантии побитового совпадения с PowerPoint, особенно при сильном увеличении. Палитра включает тему и поддерживаемые преобразования цвета, совместный цвет заливки применяется до создания PNG. PNG и их внутренние relationships/content types входят в прежние лимиты размера; внешние ресурсы не добавляются, коллизии служебных имён отклоняются.

**Позиции остановок:** буквальное имя `tayga:gradient-stops` является профилем Tayga для обоих форматов, а не штатным именем эффекта PowerPoint/Impress. Для PPTX используется `p:anim valueType="str"`, для ODP — `anim:animate`. `from`, `to` и `by` задают списки из 2–16 чисел через запятую; позиции нормированы в 0–1, относительные приращения — в −1…1. Операнд to имеет приоритет над by. Количество значений должно совпадать с исходными остановками, явно заданный from — с их сохранёнными позициями. Начальный и конечный массивы должны быть неубывающими и находиться в 0–1; поэтому линейная интерполяция сохраняет порядок на всём интервале. Совпадающие позиции допускаются для резкой границы, пересечение и добавление/удаление остановок не поддержаны. Цвет каждой остановки сохраняется, пока отдельный цветовой эффект не меняет палитру.

Пример PPTX: `<p:anim valueType="str" from="0,1" to="0.2,0.8">…</p:anim>` с `p:attrName` равным `tayga:gradient-stops`; ODP: `<anim:animate smil:attributeName="tayga:gradient-stops" smil:targetElement="shape" smil:dur="1s" smil:to="0.2,0.8"/>`. В обоих случаях остаются обязательными поддерживаемая emphasis-последовательность и существующая цель. В API property=`stops` содержит массивы from/to вместо одного числа; размеры фокуса имеют property=`focus-width`/`focus-height`. Браузер проверяет длины, значения и порядок. Неизвестные формулы, keyframes и свойства не исполняются.

PPTX изменяет только pos у существующих gs, сохраняя цвета и порядок XML. ODP копирует существующие RGB gradient-stop LibreOffice либо разворачивает стандартный двухцветный градиент в две явные остановки с исходными позициями 0 и 1. Общие именованные градиенты и стили остаются неизменными. Поддержка отрисовки расширенных остановок зависит от конвертера; локальный LibreOffice проверен, другие офисные серверы требуют отдельной приёмки. Профиль анимации не гарантирует воспроизведение или сохранение этих расширений при редактировании в сторонних офисных программах.

Прежние пределы сохранены: девять обычных геометрических состояний (два для discrete), совместная сетка до 45 пар состояний, 120 PDF-страниц на версию, 12 эффектов на слайд и один эффект геометрии на объект, ограничения XML/ZIP/PDF/стилей и параллелизма. Отсутствие поддержки или недопустимые параметры дают статичный слайд с предупреждением; превышение ресурсного лимита останавливает подготовку.

Проверки: `file_compare_motion_gradient_stops_test.go` проверяет размеры обеих осей, сохранение центра, выход за границы, растровую заливку, позиции 2/3 остановок и относительные приращения, приоритет to и отказ при изменении количества/пересечении/нечисловых значениях. `node scripts/check-file-motion-gradient-stops.mjs` использует настоящий PDF.js с тестовыми PDF: движущиеся остановки с независимо запаздывающим цветом, расширение фокуса, перемотка, разница кадров, навигация, мобильная ширина, некорректные манифесты и закрытие при смене аккаунта. `TAYGA_TEST_OFFICE_RENDER=1 go test ./internal/httpapi -run TestMotionJointGradientRealOffice -v` отрисовывает через LibreOffice/Poppler размеры по обеим осям и центрированный круговой фокус PPTX, остановки PPTX/ODP и совместные эффекты с цветом заливки.

Контракты: [Microsoft — атрибуты анимации, включая fill.focussize.x/y](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.presentation.attributename), [LibreOffice — импорт градиента и fillToRect](https://github.com/LibreOffice/core/blob/master/oox/source/drawingml/fillproperties.cxx), [OASIS — OpenDocument 1.3, Part 3](https://docs.oasis-open.org/office/OpenDocument/v1.3/os/part3-schema/OpenDocument-v1.3-os-part3-schema.pdf).

### Подробное сравнение оформления, диаграмм и анимации (5 ноября 2026)

Для XLSX/ODS/PPTX/ODP в истории выберите «Подробное сравнение». Он включает прежнее сравнение содержимого и добавляет карточки оформления ячеек/строк/столбцов, разметки листов/слайдов, тем/макетов/стилей, диаграмм, переходов и анимации. Исходники не изменяются. Офисный сервер для этого режима не требуется. Это сравнение сохранённых параметров, а не изображений отрисованных страниц: эффекты не исполняются, формулы не пересчитываются, переходы не воспроизводятся.

**XLSX:** раскрываются font/fill/border/numFmt и родительский XF выбранного стиля, отдельно учитывается базовый стиль книги. Перенумерация одинаковых font/cellXf не создаёт правку. Учитываются размеры/свойства строк и столбцов, объединения, параметры страницы, фильтры, условия форматирования и рисунки листа; курсор выделения исключён. Номера dxf заменяются отпечатками определений. Представление не является полным вычислителем итогового стиля с учётом всех правил Excel.

**PPTX:** сравниваются свойства фигур, координаты/размеры, заливки/линии, текстовые свойства, параметры презентации и ссылки на используемые макеты/мастера/темы. Определения наследуемых частей выводятся отдельно. В текстовых фрагментах последовательные одинаковые стили объединяются; для смешанного оформления учитываются длины фрагментов. Переходы и timing сравниваются отдельными карточками, включая эффекты, длительности и цели. Служебные cNvPr/cTn/axis IDs нормализуются с сохранением ссылок на соответствующие объекты. Разбиение однородного текста на несколько одинаково оформленных run само по себе не является сменой оформления.

**ODS/ODP:** используются стили из content.xml/styles.xml с разрешением родительских стилей, шрифтов, master/page-layout/data-style. Неиспользуемые именованные стили не перечисляются. В ODS сохраняются привязки оформления и геометрия таблицы, значения/формулы исключены из карточки разметки, поскольку сравниваются отдельно. В ODP сравниваются свойства страниц/фигур, SMIL/legacy-анимация и параметры переходов из drawing-page style. Основные XML ID целей анимации нормализуются. Не все сложные выражения событий SMIL и варианты наследования эквивалентны при таком структурном сравнении.

**Диаграммы:** для OOXML читаются связанные chart parts, их параметры, серии/формулы и сохранённые данные, а также chartStyle/chartColorStyle. Номера relationships и осей не служат идентичностью данных. В отличие от кеша формульной ячейки, кеш диаграммы включён в сравнение: он хранит данные отображаемого графика. Для ODF читаются локальные внедрённые chart objects с content.xml; неизвестные типы объектов отклоняются. Внешние диаграммы/стили не загружаются. Внешние ссылки остальных поддерживаемых свойств сравниваются как строки, изображения и бинарные зависимости — по SHA-256. Это не проверка внешнего источника данных или визуальной эквивалентности диаграмм.

API принимает `mode=details` и возвращает прежний структурный ответ с `details=true` и дополнительными section: cell-style/row-style/column-style/sheet-layout/sheet-chart/slide-style/slide-chart/slide-transition/slide-animation/presentation-layout/theme. В «Было / Стало» выводятся пути сохранённых свойств и значения. Размеры шрифта подписаны в pt, координаты — в mm с исходными EMU, целые временные значения — в ms; округление для показа не участвует в сравнении. XML-префиксы имён и порядок атрибутов не определяют равенство; известные ссылки на стили/объекты разрешаются до сравнения. При этом явные свойства, неявные значения по умолчанию и эквивалентные способы записи могут различаться: это не универсальная нормализация всех офисных схем.

Права истории остаются владельческими. Обе стороны открываются тем же способом, что для базового режима, без записи, новых офисных токенов или внешних запросов. Лимиты ZIP/XML прежние; для подробного результата — до 30 000 записей/16 MiB данных на сторону, до 4000 свойств/256 KiB на один отчёт. Ограничены глубина зависимостей и наследование, циклы/неизвестные ссылки возвращают 422 вместо неполного результата. Сложные формулы, бинарные XLS/PPT, неизвестные расширения диаграмм/объектов и фактическая отрисовка остаются отдельными задачами.

`file_compare_details_test.go` проверяет шрифт без правки содержимого, перенумерацию XLSX-стилей, PPTX-шрифт/переход/длительность при неизменном тексте, служебные ID объектов/времени/осей/relationships, данные диаграммы, ODS/ODP-стили, SMIL и внедрённую ODF-диаграмму, циклическое наследование, изоляцию истории и неизменность файла. Встроенные реальные XLSX/PPTX проходят разбор. Браузерный тест проверяет выбор нового режима, названия секций и мобильную компоновку. Внешний движок не использовался для доказательства визуальной эквивалентности; приёмка реальных сложных файлов остаётся отдельно.

Форматы: [Open XML — Animation](https://learn.microsoft.com/en-us/office/open-xml/presentation/working-with-animation), [Slide layouts](https://learn.microsoft.com/en-us/office/open-xml/presentation/working-with-slide-layouts), [OpenDocument 1.3](https://docs.oasis-open.org/office/OpenDocument/v1.3/os/part3-schema/OpenDocument-v1.3-os-part3-schema.html).

## WebDAV

Адрес личного хранилища:

```text
https://mail.example.com/dav/files/
```

Поддерживаются GET/HEAD, PUT, PROPFIND, MKCOL, COPY, MOVE, DELETE, LOCK/UNLOCK и ETag. DELETE перемещает в корзину. Блокировки действуют также на запись из веба и офиса. PUT принимает `If-Match` и `If-None-Match: *`; неполные загрузки отклоняются. Лимит одного файла — 10 ГиБ, данные записываются потоком во временный файл.

Используйте обычный клиент WebDAV с HTTPS. Логин — полный почтовый адрес, пароль — пароль учётной записи. Passkey относится только к веб-входу. При включённом TOTP и политике `mfa.require_token_for_mfa_users` нужен клиент с поддержкой Bearer-токена; обхода этой политики в WebDAV нет. Собственный протокол синхронизации Nextcloud, его discovery/account API и совместимость с его chunk API пока не реализованы. Возобновляемая загрузка в веб-интерфейсе Tayga описана ниже.

### Общие файлы и папки (5 ноября 2026)

В окне «Подключить WebDAV» доступны два адреса: личное хранилище и общие папки. Общий раздел подключается по `https://mail.example.com/dav/shared/`, отдельный владелец — по `https://mail.example.com/dav/shared/owner@example.com/`. Вход выполняется собственной учётной записью получателя доступа. `PROPFIND` общего раздела с Depth 0/1 показывает только владельцев с действующими доступными файлами; для просмотра их содержимого клиент открывает каталог владельца. Рекурсивный PROPFIND корня общего раздела отклоняется; рекурсивное чтение внутри каталога владельца фильтрует недоступные пути.

Виртуальные родительские каталоги позволяют пройти к выданной вложенной папке, не открывая её соседей. Права read разрешают просмотр/скачивание, write — также PUT, MKCOL, DELETE, COPY/MOVE и LOCK/UNLOCK в разрешённых путях. Управление ACL остаётся в вебе/API; полноценный WebDAV ACL discovery не заявляется. Публичные ссылки в этот раздел не подключаются. Отозванный доступ исчезает из списка и блокирует новый запрос; право записи повторно проверяется при завершении загрузки. Уже скачанные данные не отзываются.

Данные хранятся у владельца: общая запись видна в вебе, расходует его квоту, создаёт его версии и при DELETE перемещается в его корзину. История и корзина не раскрываются получателю. Блокировки личного и общего DAV относятся к одному файлу и препятствуют конфликтующим записям также из веба/офиса. ETag проверяется до загрузки и при commit; неполный, конкурентный, отозванный или превышающий квоту PUT не заменяет прежний файл.

COPY/MOVE поддерживаются между доступными путями внутри каталога одного владельца. Запись в недоступный путь и перенос между личным/общим подключениями либо разными владельцами отклоняются. В общем DAV перезапись существующей цели COPY/MOVE отклоняется, в том числе с Overwrite:T: цель не удаляется до потенциально неуспешного копирования. PUT существующего файла с проверкой версии поддерживается. Рекурсивный COPY каталога не является общей транзакцией всех его файлов; при ошибке могут остаться уже скопированные новые элементы, исходные файлы сохраняются.

HTTP-проверки `file_dav_shared_test.go` покрывают обнаружение, скрытие соседей, read/write, отзыв/понижение прав, запрет LOCK читателю, общие блокировки владельца/редактора, COPY/MOVE/корзину, обход путей, сохранность цели при отказе, отзыв во время загрузки, конкурирующие записи и квоту владельца. Приёмка Finder/Windows WebDAV и других настольных клиентов выполняется отдельно. Протокол: [RFC 4918](https://www.rfc-editor.org/rfc/rfc4918.html).

## Collabora Online (WOPI)

Collabora устанавливается отдельно от почтового сервера. Подключение в Tayga: **Администрирование → Настройки сервера → Хранение и доступность → Файлы и офис → office_url**. Пример bootstrap-конфигурации:

```yaml
http:
  public_url: https://mail.example.com
files:
  office_url: https://office.example.com
```

Пустой `office_url` отключает офисную интеграцию. Изменение адреса через настройки применяется без перезапуска; уже выданные сеансы для прежнего адреса прекращают работать.

Для запуска нужны:

1. Действующий HTTPS на обоих адресах. Внешний адрес Tayga должен быть доступен с офисного сервера.
2. `/hosting/discovery` на сервере Collabora; URL редактора в ответе должен относиться к тому же HTTPS-хосту, что и `office_url`.
3. Разрешённый WOPI-хост `mail.example.com` в конфигурации Collabora. Обратный прокси должен пропускать WebSocket редактора и WOPI-запросы; его ограничения размера и времени должны соответствовать документам.
4. Сохранение query string и заголовков `X-WOPI-*`, `X-COOL-WOPI-Timestamp` в обратных запросах. Не записывайте `access_token` в журналы прокси.

Браузер отправляет в iframe Collabora отдельный токен документа методом POST. Пароль пользователя и токен входа Tayga не передаются. Срок токена — 8 часов; токен ограничен пользователем и документом, а текущие права и состояние учётной записи проверяются при обратных запросах. Общий файл открывается в режиме просмотра либо редактирования согласно ACL. Для совместной работы участники получают одинаковый `WOPISrc`, но разные токены.

Реализованы CheckFileInfo, GetFile, PutFile, PutRelativeFile, Lock, RefreshLock, Unlock, UnlockAndRelock и GetLock. Поддерживается проверка времени изменения Collabora при сохранении без блокировки. При наличии proof-key в discovery проверяются RSA/SHA-256 подпись запроса, URL, токен и допустимое время. Для собственного сервера рекомендуется включить proof keys (`coolconfig generate-proof-key`). Создание из шаблонов и текстовое сравнение версий доступны через файловый интерфейс, см. выше; нативное сравнение Collabora остаётся отдельным расширением.

### «Сохранить как» через WOPI (5 ноября 2026)

`POST /wopi/files/{id}` с `X-WOPI-Override: PUT_RELATIVE` создаёт копию из тела запроса в папке исходного документа. CheckFileInfo возвращает UserCanNotWriteRelative=false, когда документная сессия разрешает запись и пользователь может создавать файлы в этой папке. Право редактировать только один общий файл не открывает его соседей; операция в таком случае возвращает 501. Копирование из сессии только для чтения в личное хранилище не входит в этот шаг.

Поддержаны взаимоисключающие UTF-7 заголовки RelativeTarget и SuggestedTarget. В точном режиме недопустимое имя отклоняется, совпадение даёт 409 с X-WOPI-Lock. Перезапись другого существующего файла требует OverwriteRelativeTarget=true, отсутствия блокировки цели и сохраняет предыдущую версию. Исходный файл точным режимом не перезаписывается. В предложенном режиме расширение применяется к исходному имени, недопустимые символы заменяются, а занятое имя получает суффикс ` (1)`, ` (2)` и далее; OverwriteRelativeTarget игнорируется. Пути и переходы в другие каталоги не принимаются в точном режиме. Блокировка исходного документа не мешает создавать копию; блокировка цели учитывается также для DAV/других офисных сеансов.

Тело сначала сохраняется во временный файл с ограничением 10 ГиБ и проверкой полноты/заявленного X-WOPI-Size. Перед commit под общей блокировкой повторно проверяются сессия, состояние пользователей, источник, ACL и квота владельца. Отозванная сессия/права, неполная загрузка, квота или заблокированная цель не заменяют существующий файл. Параллельные SuggestedTarget получают разные свободные имена. Повтор SuggestedTarget после потери ответа создаёт следующую копию: операция не имеет клиентского ключа идемпотентности. Несколько серверов, совместно записывающих один root, требуют отдельной координации.

Ответ содержит Name и HTTPS Url нового WOPI-файла с отдельным токеном, ограниченным новым файлом, тем же пользователем и исходным сроком сессии. Старый токен не открывает новую копию, новый не открывает исходник. Сохраняются проверки proof-подписи и смены провайдера/URL. Возвращаемый Url содержит секрет доступа: его нельзя публиковать или записывать в диагностический журнал.

HTTP-тесты `file_office_relative_test.go` проверяют точное/предложенное имя, русский текст/UTF-7 и расширение, совпадения, блокировки WOPI/DAV, версии при явной перезаписи, защиту исходника, ограничения общего доступа и токенов, отзыв во время загрузки, ошибочные размеры/пути, параллельный подбор имени и квоту. Приёмка команды «Сохранить как» в рабочем Collabora выполняется отдельно. Протокол: [PutRelativeFile](https://learn.microsoft.com/en-us/microsoft-365/cloud-storage-partner-program/rest/files/putrelativefile).

В веб-админке откройте **Настройки сервера → Хранение и доступность → Файлы и офис · ONLYOFFICE / Р7** и выберите `office_provider: onlyoffice` или `r7`. Оба режима используют Document Server API вместо WOPI; пустой провайдер сохраняет прежнее поведение Collabora.

```yaml
http:
  public_url: https://mail.example.com
files:
  office_provider: onlyoffice # Для Р7: r7
  office_url: https://office.example.com
  office_jwt_secret: "ЗАМЕНИТЕ-ОБЩИМ-СЛУЧАЙНЫМ-СЕКРЕТОМ-ОТ-32-БАЙТ"
```

В консоли `tayga menu` доступен отдельный пункт **Настройки сервера → Файлы и офис (Collabora / ONLYOFFICE / Р7)**: отключение редактора, выбор провайдера, HTTPS-адрес и JWT-секрет. Пустой ввод секрета сохраняет прежнее значение. Консоль записывает настройки в БД; уже запущенную службу после такого изменения нужно перезапустить. Изменения из веб-админки применяются сразу.

Установите Document Server отдельно, с действующим HTTPS. Браузер должен видеть оба адреса; Tayga и офисный сервер должны обращаться друг к другу по HTTPS. В `local.json` Document Server включите `services.CoAuthoring.token.enable.browser`, `token.enable.request.inbox` и `token.enable.request.outbox`. Задайте тот же секрет для `services.CoAuthoring.secret.inbox.string`, `secret.outbox.string` и, в версиях с отдельным параметром, `secret.browser.string`. Для callback используются HS256 и стандартный заголовок `Authorization: Bearer …`; также поддержан JWT в поле `token` тела запроса. Секрет скрывается в настройках Tayga и не передаётся браузеру.

В обратном прокси Tayga пропускайте `/office/document/` с GET и POST, сохраняя query string и `Authorization`. Исключите `access_token` из журналов. Прокси офисного сервера должен поддерживать WebSocket и обычные пути Document Server, включая `/web-apps/apps/api/documents/api.js`. Если офисный сервер запрещает обращения к частным IP, настройте доступ к адресу Tayga согласно документации своей версии.

Открытие: **Файлы → выбрать документ → Открыть в офисе**. Поддержаны DOC/DOCX, ODT, RTF, TXT, XLS/XLSX, ODS, CSV, PPT/PPTX и ODP. Для сохранения исходных форматов, отличных от OOXML, включите `services.CoAuthoring.server.assemblyFormatAsOrigin` в Document Server. Если callback сообщает другой формат, Tayga отклоняет сохранение: содержимое DOCX не должно попадать в файл с расширением ODT или DOC. На первом стенде используйте DOCX/XLSX/PPTX.

Права просмотра/редактирования берутся из ACL Tayga и повторно проверяются при загрузке и сохранении. Участники получают общий `document.key`, а после завершения сеанса — новый ключ, чтобы исключить открытие устаревшего документа из кеша. Редактирование блокирует конкурирующую запись из веба и WebDAV. Сохранение создаёт версию и учитывает квоту владельца. Смена URL, провайдера или JWT-секрета отзывает выданные сеансы; токены и блокировки ограничены восемью часами и не переживают перезапуск Tayga.

Кнопка сохранения находится в редакторе (`forcesave`). Callback со статусом 6 сохраняет промежуточное состояние; статус 2 сохраняет итог и снимает блокировку, статус 4 завершает сеанс без изменений. После закрытия последнего редактора Document Server обычно отправляет итоговый callback с задержкой; обновите список файлов после завершения сохранения. URL сохранённого файла принимается только с того же HTTPS-хоста и порта, что `office_url`, без переходов по перенаправлениям.

Автоматические тесты с локальным HTTPS-стендом проверяют оба режима, JWT в заголовке и теле, совместный ключ, force-save и итоговое сохранение, историю версий, блокировки, отзыв прав и сеансов, запрет внешних URL и перенаправлений. Проверка в браузере с действующим ONLYOFFICE / Р7 пока не выполнена. При приёмке стенда откройте искусственный DOCX двумя пользователями, проверьте просмотр третьим, сохранение, закрытие и повторное открытие, затем отзыв доступа и наличие версии в Tayga.

Протокол: [ONLYOFFICE — открытие и сохранение](https://api.onlyoffice.com/docs/docs-api/get-started/how-it-works/saving-file/), [JWT](https://api.onlyoffice.com/docs/docs-api/additional-api/signature/request/), [Р7 — callback](https://support.r7-office.ru/document_server/api-document_server/using-api-document_server/callback-handler/), [Р7 — подпись](https://support.r7-office.ru/document_server/api-document_server/more_api/signature-api/signature-2/).

## Хранение и эксплуатация

Текущие файлы: `<mailstore.root>/files/<user-id>`. Метаданные, корзина, версии и временные загрузки: `<mailstore.root>/file-state/<user-id>`. Эти каталоги должны находиться на одной файловой системе с поддержкой hard links и атомарного rename. Версии удерживают прежний inode; все управляемые операции записи заменяют файл атомарно. Внешнее изменение файлов на месте в обход Tayga не поддерживается.

Сохраняйте оба каталога вместе с полной базой данных. Существующий экспорт почтовой резервной копии из веб-админки не включает файловый сервис. Автоматическое удаление старых версий/корзины пока отсутствует. С версии 0.9.18 доступна отдельная квота файлового сервиса, описанная ниже. Прерванные процессом временные загрузки могут остаться в `file-state/*/uploads`; удалять их следует только при остановленной службе.

Блокировки и офисные токены хранятся в памяти одного HTTP-процесса. После перезапуска редактор нужно открыть заново. Для нескольких активных пишущих узлов нужны распределённые блокировки; текущая интеграция рассчитана на один активный узел.

Автоматические проверки покрывают сохранение/восстановление, отсутствие потери файла при неполной или конкурирующей загрузке, изоляцию пользователей, перенос и отзыв ссылок, обход каталогов и symlink, WebDAV Basic/Bearer, COPY/MOVE/LOCK, WOPI права и отзыв доступа, блокировки, версии и подписи. Отдельная браузерная проверка выполняется на широком экране и ширине 390 px.

Официальные [примеры Collabora](https://github.com/CollaboraOnline/collabora-online-sdk-examples/tree/master/webapp) предлагают `https://demo.eu.collaboraonline.com` и `https://demo.us.collaboraonline.com` для проверки интеграции. ## Resumable web uploads (0.9.17)

The web file picker and drag-and-drop now upload in chunks of at most 8 MiB, with the same 10 GiB per-file limit. A lost response is recovered by reading the server's acknowledged offset. After a page reload, select the same file again, or open **Files → settings → Unfinished uploads → Resume**. The browser verifies the SHA-256 of every already uploaded chunk before continuing, so a different file with the same name/size cannot corrupt the stored prefix. No file content or access token is saved to localStorage; only account-scoped upload identifiers and metadata are retained there.

Sessions and acknowledged offsets survive server restarts. The server truncates an unacknowledged partial last chunk on retry. Completing a session atomically publishes the file, preserves the previous version and checks the ETag captured at the start; a concurrent edit produces a conflict rather than being overwritten. Completion is idempotent, including recovery after a rename before the response. Shared-folder permissions are rechecked before publication, and DAV/WOPI locks are honored. History/trash are unaffected until completion.

An account can have four unfinished sessions reserving at most 20 GiB total. A session expires 24 hours after creation. Expired staging data is removed at startup, hourly and during that user's session-list/create activity. The user can cancel unfinished uploads immediately; cancellation never deletes the current file. These are staging limits, not a general file-storage quota. Versions and trash still require manual cleanup; automatic retention remains pending. Version 0.9.18 adds the storage quota described below.

API: `POST /api/v1/files/uploads` with `path`, `size`, optional `owner_id`; `GET /uploads` lists unfinished sessions; `GET /uploads/{id}` returns `upload` and accepted chunk hashes; `PATCH /uploads/{id}` accepts a bounded body and `Upload-Offset`; `POST /uploads/{id}/complete` publishes; `DELETE /uploads/{id}` cancels. All routes are under `/api/v1/files` and require the initiating user's bearer session. This is a Tayga API, not the Nextcloud chunk protocol. Back up `file-state` alongside the regular file tree if unfinished uploads must be recoverable from backups.


## Квоты файлов (0.9.18)

Поле класса обслуживания `file_quota_bytes` ограничивает хранилище каждого пользователя, которому назначен класс. Значение 0 — без ограничения. Почтовая квота независима. Считается логический размер текущих файлов, корзины и всех версий; каждая версия учитывается отдельно даже при общем физическом inode. Поэтому перезапись файла может увеличить занятое место на размер новой версии. Удаление в корзину место не освобождает; окончательное удаление из корзины и удаление версии освобождают.

Проверки общего пути записи охватывают веб, возобновляемые загрузки, WebDAV, WOPI, XMPP upload и запись через публичную ссылку. В общей папке применяется квота владельца. Финальная проверка под блокировкой предотвращает превышение лимита конкурирующими завершениями загрузок одного процесса. Временные upload-данные имеют отдельные ограничения и до публикации не входят в постоянную квоту. Квоты не являются межузловой распределённой блокировкой: совместную запись нескольких серверов в один файловый root эта реализация не координирует.

Раздел **Файлы → настройки → Место в хранилище** показывает текущие файлы, корзину, версии и доступный остаток. API `GET /api/v1/files/library/usage`; удаление одной версии — `DELETE /api/v1/files/library/versions` с `id`. Нехватка квоты возвращает HTTP 507 без частичной замены текущего файла. Понижение квоты ниже занятого места не удаляет данные; новые записи блокируются до освобождения места или повышения лимита.
