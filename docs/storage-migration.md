# Полная миграция SQLite → PostgreSQL

`migrate-storage` переносит все физические прикладные таблицы, включая сессии,
чаты/вложения, настройки/ключи, состояния Outlook/EAS, EWS-метаданные, календарь,
контакты, задачи, ACL и историю агентов. Логический `backup` для этого не используется:
его формат предназначен для экспорта определённых сущностей и не заменяет полную
миграцию. Обратная полная миграция PostgreSQL → SQLite пока не реализована.

## Подготовка

1. Создайте полную проверенную копию установки. Остановите Tayga и внешние
   процессы, которые пишут в SQLite. Механизм проверяет эксклюзивную maintenance-
   блокировку Tayga; сторонние SQLite-инструменты обязаны соблюдать тот же режим.
2. Создайте **новую пустую** PostgreSQL БД и отдельного владельца без SUPERUSER,
   CREATEDB, CREATEROLE и REPLICATION. Уберите CONNECT для PUBLIC. На отдельном
   хосте используйте проверяемый TLS; локальный доступ ограничьте loopback.
3. Скопируйте полный исходный YAML в новый приватный файл. Измените только
   `storage.driver: postgres`, `storage.postgres.dsn` и явно сохраните прежний
   абсолютный `mattermost.attachment_directory`. Не меняйте `mailstore.root`,
   секреты, пути ключей, сертификаты, слушатели и прочие настройки.

Пример каталога вложений исходной SQLite `/var/lib/tayga/data/tayga.db`:

```yaml
mattermost:
  attachment_directory: /var/lib/tayga/data/.mattermost-attachments
```

Не передавайте DSN/пароль аргументом оболочки. Храните их в закрытом YAML,
доступном только оператору и сервисному пользователю.

## Перенос и сверка

```sh
tayga-mail migrate-storage \
  -config /var/lib/tayga/config/tayga.yaml \
  -target-config /private/tayga-postgres.yaml \
  -report /private/new-transfer-report.json
```

Тот же механизм доступен в консольном меню. Он:

- открывает SQLite только для чтения и удерживает согласованный снимок;
- проверяет внешние ключи исходника и пустоту назначения;
- перечисляет таблицы/колонки из реальной схемы; неизвестная таблица или колонка
  вызывает отказ вместо молчаливой потери данных;
- в одной транзакции временно откладывает FK и отключает прикладные триггеры,
  копирует данные через COPY, сверяет количество и мультимножество SHA-256 хешей
  полных строк для каждой таблицы, затем проверяет FK и возвращает исходные
  свойства ограничений/триггеров;
- переносит содержимое FTS5 `message_fts` в `message_search` и строит PostgreSQL
  `tsvector`; теневые FTS-таблицы/индексы и SQLite-служебные объекты не копирует.
  `mail_log_fts` заменяется поиском PostgreSQL по перенесённому `mail_log`.
  Таблица версий миграций создаётся миграциями PostgreSQL, а не версиями SQLite;
- нормализует типизированные SQL timestamps к UTC с точностью PostgreSQL до
  микросекунды. Текст ICS/VCF/MIME/JSON и целочисленные UID/счётчики не меняются;
- не меняет исходную SQLite, почтовые файлы и активный конфиг.

Отчёт mode 0600 содержит имена таблиц, количества, отпечатки, исключения и общий
`verified: true` только после успешного COMMIT. Ошибка откатывает данные и временные
изменения схемы. Непустую целевую базу механизм не перезаписывает. Повреждённые FK,
неподдерживаемые типы и NUL в PostgreSQL TEXT не исправляются молча.

## Переключение

После успешной сверки сохраните исходный YAML/SQLite для восстановления,
установите целевой YAML и запустите Tayga. Проверьте вход существующей сессией,
почту/поиск, календарь/задачи, доступ к файлам и фото Mattermost, EWS/EAS и журналы.
Сделайте `pg_dump -Fc` основной БД и отдельных баз Boards/Playbooks.

После появления новых записей в PostgreSQL не переключайтесь обратно на старую
SQLite: это потеряет новые данные. Для отката приложения сохраняйте PostgreSQL
либо сначала готовьте отдельный согласованный обратный перенос. Старые SQLite-
снимки `backup-full` не заменяют резервирование действующей основной PostgreSQL:
для неё нужен согласованный pg_dump/физический backup вместе с файловой установкой.

Большие состояния Outlook/EAS в TEXT сжимаются штатным PostgreSQL TOAST. Настройки
сжатия меняют физическое представление, сохраняя содержимое и ключи клиента.
Не удаляйте все `flowsync_states` по общему TTL: таблица также содержит квитанции
отправки и создания объектов, защищающие от повторных операций.

## Компактизация EWS/EAS без сброса ключей

Начиная со схемы 084 одинаковые `Items`-снимки хранятся один раз в пределах
пользователя и коллекции. Повторяющиеся XML-ответы хранятся отдельными общими шаблонами; личные ключи
заменяются обратимыми подстановками и восстанавливаются побайтно.
У каждого контекста остаются свои Key, PreviousKey,
параметры и точный последний ответ. Снимок и оставшаяся часть состояния сжимаются
без потерь. Чтение восстанавливает исходный JSON побайтно и проверяет хеш/область.
Это не удаление почты и не сброс синхронизации.

Для уже накопленных состояний остановите Tayga и выполните:

```sh
tayga-mail compact-sync-state -config /private/tayga-postgres.yaml \
  -report /private/sync-compaction.json -apply -vacuum
```

Без `-apply` команда только показывает статистику. `-vacuum` возвращает
физическое место после успешной компактизации; для PostgreSQL используется
офлайн VACUUM FULL только таблиц состояний/снимков. Команда требует эксклюзивную
maintenance-блокировку; новые экземпляры Tayga не могут одновременно открыть БД.
Текущие и предыдущие ключи, replay XML и updated_at сохраняются. Повторная отправка
писем и задач не разблокируется: квитанции остаются без изменений.

`flowsync.state_retention_days` задаёт срок неактивности **EWS-контекстов**:
по умолчанию 180 дней, минимум 30, `0` выключает очистку. Чтение действующего
EWS-контекста обновляет отдельную отметку активности не чаще раза в час.
Работник раз в 6 часов удаляет до 1000 устаревших контекстов и неиспользуемые
снимки старше 7 дней. Квитанции submission/ews-tasks, EAS-устройства, почта,
события и задачи не удаляются. Клиент, вернувшийся после истечения срока,
выполняет полную синхронизацию. Старые поколения бинарника без поддержки схемы
084/кодека не должны запускаться на компактированных состояниях.

## Забытые мобильные устройства

В администрировании устройств «Забыть на сервере» архивирует запись и сохраняет
запрет старого Device ID. Оно не отправляет команду очистки телефона. Распознанный
кэш коллекций удаляется, квитанции повторных операций сохраняются. Показывайте
забытые записи отдельным переключателем. «Восстановить запись» очищает старую
серверную команду wipe и ключ Provision, возвращает запись **заблокированной**;
разрешение доступа выполняется отдельно. Уже выполненная очистка не отменяется,
устройство проходит Provision/синхронизацию заново.

### Некорректная кодировка старого поискового индекса

SQLite FTS мог хранить недопустимые UTF-8 байты из старых MIME-текстов. При переносе только производные поля поискового индекса нормализуются: ошибочные последовательности заменяются U+FFFD, NUL — пробелом. Число исправленных полей включается в отчёт таблицы. Та же обработка применяется к новым поисковым документам. Оригиналы MIME, метаданные писем и прочие прикладные таблицы не исправляются молча: некорректный основной TEXT останавливает перенос.
