# Межсерверные каналы Mattermost

Экспериментальная возможность в исходном коде после 1.0.5. По умолчанию выключена. Рабочая установка не обновляется автоматически.

## Два режима

- **Нативные общие каналы:** TMS ↔ TMS, протокол RemoteCluster / SharedChannel. Удалённые авторы видны как отдельные профили. Они не могут входить в TMS: это отключённые технические записи без паролей и административных ролей.
- **REST-мост API v4:** TMS ↔ TMS или оригинальный Mattermost. Удалённые сообщения доставляются через отдельного бота с указанием автора. Одна настроенная связь обслуживает оба направления; встречный мост для той же пары каналов создавать нельзя.

Совместимость нативного режима с оригинальным Mattermost требует отдельной приёмки на лицензированном Connected Workspaces. Поддержка протокольных структур сама по себе не подтверждает такую приёмку и не отменяет требований оригинального сервера. REST-мост этого механизма не использует.

## Включение на стенде

В конфигурации каждого TMS:

```yaml
mattermost:
  enabled: true
  federation:
    enabled: true
    allow_cidrs: []
```

Перезапустите стенд. HTTPS-сертификат удалённого сервера должен быть действительным. Внутренние адреса по умолчанию запрещены; администратор сервера может явно разрешить нужную CIDR-сеть в `allow_cidrs`. Не используйте широкие разрешения для публичного сервиса. Перенаправления и системный HTTP-прокси транспортом не используются.

В разделе Mattermost выберите **тенант и домен**. Администратор домена управляет только своей областью. Укажите включённого локального владельца из этого домена: он должен состоять в подключаемом канале. Связь не даёт доступа к другим каналам.

### Нативная связь

1. На первом сервере создайте нативное подключение с HTTPS-адресом второго и паролем приглашения длиной от 12 символов.
2. Передайте зашифрованный код и пароль администратору второго сервера отдельным защищённым способом.
3. На втором сервере примите код. Проверяйте адрес первого сервера до подтверждения доверия. Приглашение действует 24 часа; повторное создание отзывает предыдущий код.
4. Явно сопоставьте каналы на обеих сторонах. Для первой стороны удалённый ID можно оставить равным ID её канала. На второй стороне выберите свой канал и этот общий удалённый ID. Входящие приглашения появляются в списке ожидающих; автоматического подключения нет.

Флаг «Только отправка» запрещает удалённой стороне публикацию в локальном канале. Нативное приглашение передаёт соответствующее ограничение второй стороне.

### REST-мост

1. На удалённом сервере создайте отдельного бота и токен доступа с минимально необходимыми правами.
2. Добавьте бота только в предназначенные для обмена команду и канал.
3. В TMS создайте REST-подключение, задайте HTTPS-адрес и токен в защищённом поле.
4. Сопоставьте локальный и удалённый ID каналов. Повторите для дополнительных каналов в пределах разрешённого домена.

Обычный пользовательский токен технически возможен, но выделенный бот делает объём доступа явным. При потере HTTP-ответа мост ищет собственную метку доставки, прежде чем повторять публикацию. Это защита повторов, а не обещание транзакции между двумя независимыми серверами.

## Данные и ограничения

- Передаются новые сообщения, ветки и файлы. Размер файла ограничен 1 ГиБ на стороне TMS и собственными лимитами удалённого сервера.
- По умолчанию локальная старая история не отправляется; «Передать историю» включает её явно. В REST-режиме это также задаёт начало чтения удалённой истории. В нативном режиме удалённая сторона самостоятельно управляет своей отправкой истории.
- Обмен не является транзитным: полученные через одну связь сообщения не пересылаются в следующую.
- Личные и групповые личные чаты, реакции, аватары, статусы и подтверждения прочтения удалённых участников пока не синхронизируются. Удалённым профилям нельзя отправить локальное личное сообщение.
- Импортированные интерактивные свойства сообщений не исполняются локальными плагинами.
- Импорт поддерживает исправление текста и удаление ранее сопоставленных сообщений. Замена состава вложений существующего сообщения отклоняется. Локальные правки и удаления пока не экспортируются.
- REST-чтение ограничено 1000 сообщениями в одном окне синхронизации. При превышении обмен останавливается с ошибкой без продвижения курсора; для большого архива нужна отдельная миграция. Поиск потерянной отправки ограничен 200 000 сообщениями и также прекращается без повторной публикации при превышении границы.
- Отсутствующая в сопоставлении родительская запись ветки останавливает её доставку; старые ветки следует подключать с согласованной передачей истории. Сервис повторяет попытки, не подтверждая потерянную запись.

Токены хранятся зашифрованными ключом сервера и не возвращаются в административных ответах. Сохраняйте ключ вместе с резервной копией. Отключение подключения стирает его секреты, но сохраняет историю и таблицы сопоставления. Отключение отдельного канала прекращает его обмен. При потере владельцем доступа к каналу, блокировке владельца или отключении Mattermost для домена обмен прекращается.

Перед запуском восстановленной копии выключайте `mattermost.federation.enabled`, чтобы копия не возобновила внешнюю доставку.

## Изолированная приёмка

```sh
go test ./internal/mmfederation ./internal/httpapi -run 'TestNativePair|TestRESTPair|TestFederation|TestMattermostFederation'
```

Тесты поднимают два временных TMS с отдельными SQLite и TLS, проверяют сообщения, файлы, ветки, повторную синхронизацию, сохранение сопоставлений после перезапуска и запреты доступа.

Workflow `.github/workflows/mattermost-federation.yml` поднимает одноразовые PostgreSQL 16 и оригинальный Mattermost 12.0.0, создаёт отдельного бота и проверяет REST-мост. `TestOriginalMattermostREST` локально пропускается без `TMS_TEST_MATTERMOST_URL`; переменная допускает только HTTP на `127.0.0.1` и предназначена исключительно для одноразового сервера. Нативная приёмка оригинального лицензированного сервера в этот тест не входит.
